## 目的

ボタン、ラベル、補助文、エラー、状態の文言で、利用者が次の行動を迷わず取れるようにする。
画面が変わっても、同じ意味には同じ語と型で出会える状態を保つ。
漢字とかなの開きや英数字の空白などの表記は、別の文書で扱う。
設計文書の文体は concise-writing が扱う。

## コア

### 次の行動が読める

押した後に起きることと、直すためにすべきことを文言そのものが示す。
短さより、次の行動が読めることを優先する。

### 利用者の語と文脈で書く

作り手の分類や内部の用語ではなく、利用者が知っている語で書く。
画面が既に示している対象は、文言の中で繰り返さない。
語の正確さより、読み手に届く語を優先する。

### 責めず、煽らず、断定しない

主語は利用者ではなく入力内容や処理に置き、確かめた範囲と文言の強さを合わせる。
謝罪と重い丁寧語は、利用者に損失があるときだけ使う。
親しみより、中立で外れないことを優先する。

### 要点ごとに短く区切る

1 文は 50 字以内で要点を 1 つにする。
詰め込むより、区切りごとに要点が 1 つずつ届くことを優先する。

### 面ごとに型を 1 つに決める

同じ対象は同じ語で呼び、同じ面に並ぶ文言は同じ語形と文末に揃える。
表現の豊かさより、同じものだと判ることを優先する。

## Tips

### ボタンは押した後の行動、リンクは行き先の名前で書く

意図と根拠: 利用者はラベルから押した結果を予測して操作する。
「はい」「OK」「こちら」は、周りの文を読み直さないと結果が分からない。
対象は画面が示していれば省き、取り違えるときだけ足す。
長さは 2〜8 字に収め、収まらない説明はボタンの外の文へ分ける。

- 適用: foundation
- コア: 次の行動が読める
- コア: 利用者の語と文脈で書く
- 良い例:「保存」「詳細」、保存の対象が画面に複数あるときの「変更を保存」、送り先を示す「次の配色: 柚子」
- 悪い例:「はい」「OK」「こちらをクリック」「次へ」、「この内容で変更を保存して次へ進む」
- 例外: 検索や閉じるのアイコンのように、慣習が確立した単一目的のボタン。
- 実験: [ボタンのラベルは文脈で分かる対象を省く ADR](../decisions/2026-09-21-button-label-omits-object.md)
- 出典: [Apple Human Interface Guidelines: Writing](https://developer.apple.com/design/human-interface-guidelines/writing)

### ボタンとラベルは語幹か終止形、文は敬体で書く

意図と根拠: 同じ面で「保存」「続けます」「削除する」が混ざると、並びの関係を読み取り直す。
ボタンはサ変動詞なら語幹、それ以外は終止形で書き、ラベルは名詞で書く。
状態、補助文、エラーのように文で書くものは敬体で終える。
押せないボタンもラベルは行動のまま残し、押せない理由は隣の文で示す。

- 適用: foundation
- コア: 面ごとに型を 1 つに決める
- 良い例: ボタン「保存」「削除」「続ける」「戻る」、ラベル「メールアドレス」、文「保存しました。」
- 悪い例: ボタン「保存する」「削除します」、押せないボタンのラベルを「利用できません」に差し替える。
- 例外: 固有名詞やサービス名をそのまま引くラベル。
- 実験: [Button の見本](../../experiments/button/shared/Showcase.tsx)
- 出典: [SmartHR Design System: その他の UI テキスト](https://smarthr.design/products/contents/ui-text/app-writing/)

### 入力の条件と形式は入力前にラベルの近くで例と共に示す

意図と根拠: 条件をエラーで初めて知らせると、利用者は一度失敗してから規則を学ぶ。
プレースホルダーは入力を始めると消え、入力中に見返せない。

- 適用: foundation
- コア: 次の行動が読める
- 良い例: ラベルの下に「8 文字以上の英数字」「例: `user@example.com`」を常に出す。
- 悪い例: 条件を案内せず、入力枠のプレースホルダーにだけ「`user@example.com`」と置く。
- 例外: 日付選択のように、入力部品そのものが形式を制限する場合。
- 実験: [form-inline-validation](../records/form-inline-validation/README.md)
- 出典: [WCAG 2.2 達成基準 3.3.2](https://www.w3.org/TR/WCAG22/#labels-or-instructions)

### エラーは項目名で始め、満たすべき条件を肯定形で書く

意図と根拠: 否定形は範囲が読みにくく、「両方が含まれていません」は全部否定とも読める。
満たすべき条件を肯定形で書けば、そのまま直し方になる。
項目名で始めると、要約に並べてもどの欄の誤りかが分かる。

- 適用: foundation
- コア: 次の行動が読める
- コア: 責めず、煽らず、断定しない
- 良い例:「パスワードは英字と数字を両方含めてください。」「メールアドレスは `name@example.com` の形式で入力してください。」
- 悪い例:「パスワードに英字と数字の両方が含まれていません。」「無効な入力です。」「申し訳ありません。エラーです。」
- 例外: 認証の失敗。ID とパスワードのどちらが誤りかは伏せる。
- 実験: [form-inline-validation の UX writing レビュー](../records/form-inline-validation/evaluation/ux-writing.md)
- 出典: [GOV.UK Design System: Error message](https://design-system.service.gov.uk/components/error-message/)

### 進行、完了、失敗は同じ動詞で型を揃える

意図と根拠: 押したボタンと同じ動詞で状態を返すと、どの操作の結果かが読める。
「成功!」や感嘆符は、結果を伝えずに調子だけを強める。

- 適用: foundation
- コア: 面ごとに型を 1 つに決める
- コア: 責めず、煽らず、断定しない
- 良い例:「保存しています」「保存しました」「保存できませんでした」
- 悪い例:「処理中…」「成功しました!」「エラーが発生しました」
- 例外: 操作に結び付かない初回の読み込み。動詞を「読み込む」にして同じ型で書く。
- 出典: [Windows Admin Center: UI text and design style guide](https://learn.microsoft.com/en-us/windows-server/manage/windows-admin-center/extend/guides/ui-text-style-guide)

### 状態の文言は 2 文以内で、起きたことを先、次の行動を後に書く

意図と根拠: 状態の文言は操作の合間に一瞥で読まれ、3 文目からは読まれにくい。
空、完了、失敗のどれも、1 文目で状態を、2 文目で次にできることを伝えれば足りる。

- 適用: foundation
- コア: 次の行動が読める
- コア: 要点ごとに短く区切る
- 良い例:「まだ記録がありません。右上の追加から作れます。」
- 悪い例: 理由も行動も無い「データがありません」、経緯を 3 文以上で説明する空状態。
- 例外: 規約や法令の引用のように、原文を変えられない文。
- 出典: [Nielsen Norman Group: Designing Empty States in Complex Applications](https://www.nngroup.com/articles/empty-state-interface-design/)

### 確認は結果を問いにし、ボタンは結果の語にする

意図と根拠: ボタンが「はい」「いいえ」だと、問いを読み直さないと結果が分からない。
急いでいる利用者は、問いを読まずに押してしまう。
問いに対象と結果を書き、ボタンにはその結果の語を置く。
辞退する側を貶める文言は、利用者を感情で誘導する。

- 適用: foundation
- コア: 次の行動が読める
- コア: 責めず、煽らず、断定しない
- 良い例: 問い「この下書きを削除しますか?」、ボタン「削除」「キャンセル」
- 悪い例: 問い「本当によろしいですか?」、ボタン「はい」「いいえ」、辞退の「いいえ、損をしてもかまいません」
- 例外: 取り消せる操作。確認を出さず、取り消しで守る。
- 出典: [Apple Human Interface Guidelines: Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts)

### 文言は 1 文を 1 つの文字列で持ち、断片を連結しない

意図と根拠: 断片をつなぐと、語順、助詞、空白を組み立て側が仮定してしまう。
言語や語を差し替えたとき、仮定した語順が崩れて文にならない。

- 適用: foundation
- コア: 面ごとに型を 1 つに決める
- 良い例:「入力内容に {count} 件の問題があります」を 1 つの文字列で持ち、数を差し込む。
- 悪い例: `${title}の索引` や「保存」と「しました」のように、語の断片をコードでつなぐ。
- 例外: 固有名詞や数値だけを差し込む場合。差し込む位置は文字列の側で決める。
- 実験: [方針画面の実装](../../apps/catalog/src/pages/GuidelinesPage.tsx)
- 出典: [Microsoft Globalization: String concatenation](https://learn.microsoft.com/en-us/globalization/internationalization/concatenation)
