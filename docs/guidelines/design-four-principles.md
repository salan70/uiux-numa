## 目的

UI の可読性と操作性を保ち、情報の所属・重要度・役割を視覚的に伝える。
情報の構造と順序は [Information Architecture](information-architecture.md)、視覚表現は本稿、文言は [UX Writing](ux-writing.md) が扱う。
近接・整列・反復・対比は目的を達成する手段であり、白黒や角丸など特定の作風を全製品に強制しない。

## コア

### 読み取りと操作を成立させる

必要な情報と操作を見分けられる状態を保つ。
見た目を揃えるために、文字、操作の手がかり、内容を削らない。

### 見た目を意味に対応させる

所属と重要度を、距離・配置・強さで表す。
関係する要素は意味のある基準へ揃え、意図してずらすならそのずれが示す関係を明確にする。
装飾の配置は、対称や均等のためであっても情報の関係を誤って見せない範囲で決める。

### 同じ役割の表現を繰り返す

同じ役割には共通の表現を使う。
役割や内容が違うものまで同じ形に押し込むことより、意味に合う違いを保つ。

### 全体の規則を保って細部を整える

余白・文字・線・形に共通の規則を使う。
機械的な数値一致より、実寸での整い方と意図した印象を確かめる。

上の順序は本稿内の判断に使う。
コア 1 を満たす案の中で、コア 2、3、4 の順に判断する。
この順序を Color や Information Architecture を含む全ガイドラインの優先順位へ広げない。

## Tips

### 余白と境界で所属を明確にする

意図と根拠: 余白で分ける場合は、同じ組の内側を組どうしの間隔より近づける。
幅や内容の制約で所属が曖昧になる場合は、見出しや囲みを補う。
近接と[共通領域](https://www.nngroup.com/articles/common-region/)はどちらもまとまりを伝えるため、囲みと余白が違う所属を示すと誤読を招く。
余白の例では space.200 と space.600 を使えるが、8px / 24px や 3 倍の差を必須条件にしない。

- 適用: foundation
- コア: 見た目を意味に対応させる
- 良い例: 入力ラベル・入力欄・補足を 1 組にし、組内に space.200、次の項目との間に space.600 を使う例のように余白を分ける。
- 悪い例: 補足文が次の入力欄に近く、どちらの説明か分からない。
- 例外: 表では行・列の境界や見出しが所属を示すため、余白の比率だけで良否を決めない。
- 実験: [Space tokens](../../tokens/space/README.md)
- 出典: [NN/g: Proximity](https://www.nngroup.com/articles/gestalt-proximity/)

### 読む方向と比較する項目に沿って揃える

意図と根拠: 配置と整列で、所属・重要度・読む順や比較関係を伝える。
関係する要素は、互いの端や中心、レイアウトの基準線など意味のある基準へ揃えることを原則とする。
意図してずらす場合は、そのずれが示す役割や関係を明確にする。
基準は役割ごとに選び、総数を制限しない。Carbon Grid は複数の列と基準線を持つ実例である。

- 適用: foundation
- コア: 見た目を意味に対応させる
- コア: 全体の規則を保って細部を整える
- 良い例: 日本語の横書き説明は読み始めを揃え、金額の比較列は桁を揃える。
- 悪い例: 同じ説明一覧で開始位置を不規則にずらし、金額を個別に中央揃えする。
- 例外: 短い題字や独立した案内の中央揃え、RTL の開始端、意図した非対称構図を許容する。中央揃えにも中心の基準があり、本文の両端揃えは求めない。
- 出典: [Carbon: 2x Grid](https://carbondesignsystem.com/elements/2x-grid/overview/)

### 判断するまとまりごとに強調の差を付ける

意図と根拠: 視覚階層は、その場で情報が担う重要度を伝える。
サイズ・太さ・余白・位置などで差を付け、重要度が対等なら同じ強さで示す。
一画面に主役を 1 つだけ置く一律の制限は設けない。
配色は Color の役割色、コントラストは Accessibility の条件に委ね、ここで閾値を再定義しない。

- 適用: foundation
- コア: 読み取りと操作を成立させる
- コア: 見た目を意味に対応させる
- 良い例: 保存操作を強調しつつ別領域の入力エラーも明確にし、対等な商品比較は同じ強さで示す。
- 悪い例: 見出し・補足・ボタンをすべて同じ強さにする。または主役を守るためエラーを薄くして読めなくする。
- 例外: 監視画面など、複数の重要情報を同時に認識する用途では局所的な強調を併存させる。
- 出典: [NN/g: Visual Design Principles](https://www.nngroup.com/articles/principles-visual-design/)

### 文字の役割に既存のスタイルを割り当てる

意図と根拠: 既存の semantic typography は、文字の役割ごとに表現を再利用するためのものである。
採用済みの token の個数から、画面内の階層数を制限しない。
行長や文字サイズの値は [Typography tokens](../../tokens/typography/README.md) の正本へ委ね、CSS の文字サイズと意味上の見出し階層を同一視しない。

- 適用: foundation
- コア: 読み取りと操作を成立させる
- コア: 同じ役割の表現を繰り返す
- コア: 全体の規則を保って細部を整える
- 良い例: heading と body を役割で使い分け、同じ役割では書体・太さ・行間を揃える。
- 悪い例: 各カードの収まりだけを理由に、同じ説明文を 13px、14px、15px と変える。
- 例外: 採用済みの組だけで役割を表せない場合は、不足と利用例を記録して追加を検討する。タイトル表現や別 platform の書体を一律に禁じない。
- 実験: [Typography tokens](../../tokens/typography/README.md)

### 操作と状態の違いを見た目でも区別する

意図と根拠: 類似した外観は、類似した機能を期待させる。
操作の手がかりが弱い場合の負担は [NN/g の研究例](https://www.nngroup.com/articles/flat-ui-less-attention-cause-uncertainty/)で扱われているが、その効果をすべての UI に一般化しない。
状態の遷移や通知の時期は [States & Feedback](states-and-feedback.md)、意味の実装は [Accessibility](accessibility.md) が扱う。
色だけで伝えない要件は [WCAG 2.2: Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html) に従い、色の役割とコントラスト条件はここで再定義しない。

- 適用: foundation
- コア: 読み取りと操作を成立させる
- コア: 見た目を意味に対応させる
- コア: 同じ役割の表現を繰り返す
- 良い例: リンクの表現を揃え、選択中の項目には下線やチェックも添え、必要な状態を支援技術にも伝える。
- 悪い例: 押せないラベルを同じ画面のボタンと同じ外観にする。または選択状態を微妙な色差だけで示す。
- 例外: 採用した OS 標準部品は標準の手がかりを使い、独自の造形へ置き換えることを必須にしない。
- 出典: [NN/g: Flat UI and Uncertainty](https://www.nngroup.com/articles/flat-ui-less-attention-cause-uncertainty/)

### 繰り返す項目は読む位置を揃え、内容量には追従させる

意図と根拠: 同じ種類の項目は、題名・主要値・補足の相対位置と順を揃える。
同じ型をたどれることと、すべての項目の高さを等しくすることは別である。
任意項目で段を揃える候補は未検証であり、その効果が確定した原則として扱わない。

- 適用: foundation
- コア: 読み取りと操作を成立させる
- コア: 同じ役割の表現を繰り返す
- 良い例: 商品一覧で名前と価格の位置関係を揃え、長い名前は折り返して表示する。
- 悪い例: 項目ごとに価格の位置を変える。または高さを揃えるため重要な名前を隠す。
- 例外: 比較表は行と列を優先する。種類の異なる成果物には内容に合う型を使う。任意項目の有無は許容し、全項目を同じ段数やカードにしない。
- 実験: [任意項目で段の数を変えない候補](../../docs/principles/block-shape-must-not-vary-by-optional-parts.md)
- 出典: [NN/g: Similarity](https://www.nngroup.com/articles/gestalt-similarity/)

### 幅と文字量が変わっても意味のまとまりを保つ

意図と根拠: 狭い幅や文字量の変化に応じて再配置し、ラベルと対象、説明と見本の対応を保つ。
視覚だけに存在する関係は [WCAG 2.2 の Info and Relationships](https://www.w3.org/WAI/WCAG22/Understanding/info-and-relationships.html) が扱う要件を満たさない場合がある。
Reflow の規範的な条件は [WCAG 2.2 1.4.10](https://www.w3.org/TR/WCAG22/#reflow) に従う。

- 適用: foundation
- コア: 読み取りと操作を成立させる
- コア: 見た目を意味に対応させる
- 良い例: 左右に並ぶ比較を狭い幅で縦に並べ、各例の名前と意味のある読み順を保つ。
- 悪い例: PC 版を全体縮小する。または CSS の並べ替えで視覚順と読み上げ順を食い違わせる。
- 例外: 本質的に二次元で読む表や図は、関係を保てる局所スクロールなどを使う。例外をページ全体へ広げない。
- 出典: [WCAG 2.2: Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

### 独自の造形は実寸で見かけを合わせる

意図と根拠: 独自のアイコン・図形・題字は、数学的な中心と寸法を出発点にする。
周囲と並べた実寸で見かけの重さや位置を整え、外接矩形が同じだけで完成としない。
制作手順は [SVG 制作 Skill](../../skills/crafting-svg/SKILL.md) に委ねる。

- 適用: module
- コア: 全体の規則を保って細部を整える
- 良い例: 再生三角形と円形記号を同じ操作枠に置き、必要なら描画部分だけを調整する。
- 悪い例: すべてを同じ bounding box に収めただけで揃ったと判断する。または見かけを合わせるため操作領域を小さくする。
- 例外: ブランド指定や配布素材の改変制約を優先し、必要なら配置側で調整する。データ量を表す形は意味を変えない。万能な補正値は設けない。
- 実験: [SVG 制作 Skill](../../skills/crafting-svg/SKILL.md)
- 出典: [Carbon: Pictograms — Alignment](https://carbondesignsystem.com/elements/pictograms/usage/#alignment)
