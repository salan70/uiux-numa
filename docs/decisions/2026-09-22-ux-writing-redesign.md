# UX Writing を部品と状態の文言に絞って組み直す

- 状態: Accepted
- 日付: 2026-09-22
- 参照: [コアの数値 ADR](2026-09-21-guideline-core-values.md)、[ボタンのラベルは文脈で分かる対象を省く ADR](2026-09-21-button-label-omits-object.md)
- 対象: `docs/guidelines/ux-writing.md`

## 背景

UX Writing の Tips は 15 件あり、書式の目安 8 件の約 2 倍だった。
5 件はコア「要点ごとに短く区切る」の言い換えに近く、4 件は Catalog の見本帳に固有の規則だった。
評価観点 `ux-writing` は `localization robustness` 軸を担当するが、frontmatter にも Tips にも無かった。
調子、ボタンの語形、状態と確認の文言を扱う規則も無かった。

利用者は 2026-09-22 に、既存にとらわれず 0 から設計し直すと決めた。
範囲を広く洗い出したあと、次の順で利用者と収束させた。

1. 対象範囲、表記の置き場、調子の扱い、既存 ADR の扱い
2. コアの数値、ボタンの語形、Tips の導き方
3. Tips 8 件の方向、調子と誠実さの畳み方

## 決定

- 対象を部品と状態の文言に絞る。ボタン、リンク、入力ラベル、補助文、エラー、空、読み込み、完了、失敗、確認を扱う。
- 通知、メール、ストア説明のような画面外の文言は扱わない。
- 画面文言の表記は別の文書へ切り出す。今回は目的に境界の 1 文だけ置き、新しい文書は作らない。
- 調子と誠実さはコア「責めず、煽らず、断定しない」の 1 件に畳む。プロダクトごとの人格は扱わない。
- コアは 5 件にする。優先順は次のとおり。
  1. 次の行動が読める
  2. 利用者の語と文脈で書く
  3. 責めず、煽らず、断定しない
  4. 要点ごとに短く区切る
  5. 面ごとに型を 1 つに決める
- 1 文 50 字は、コアの数値 ADR の値をそのまま継承する。
- 既存 Tips はすべて捨て、部品と状態ごとに書き手が決めることから 8 件を導く。8 件とも `foundation` にする。
- ボタンの語形は、サ変動詞なら語幹、それ以外は終止形に統一する。
  ボタンのラベル ADR の「面ごとにどちらかへ揃える」を置き換える。
- ボタンは対象を文脈で省き、2〜8 字に収める。ボタンのラベル ADR の決定を継承する。
- `axes` に `localization robustness` を足し、Tip「文言は 1 文を 1 つの文字列で持ち、断片を連結しない」で受ける。

## 理由

### 対象範囲

画面外の文言まで含めると、Tips 8 件に部品、状態、流れ、通知が同居する。
部品と状態に絞れば、場面ごとに 1 件ずつ規則を置ける。
読み上げ専用の文言は Accessibility、出すタイミングと取り消しは States & Feedback が既に扱っている。

### Tips の導き方

既存 Tips を縮める方法では、書き足した順の偏りが残る。
部品と状態ごとに書き手が決めることを挙げ、そこから規則を導いた。

| 部品と状態           | 書き手が決めること                   | Tip                                                         |
| -------------------- | ------------------------------------ | ----------------------------------------------------------- |
| ボタン、リンク       | 行動の語、対象の有無、長さ、行き先   | ボタンは押した後の行動、リンクは行き先の名前で書く          |
| 全部品               | 語形と文末                           | ボタンとラベルは語幹か終止形、文は敬体で書く                |
| 入力ラベル、補助文   | 条件と形式をいつどこで示すか         | 入力の条件と形式は入力前にラベルの近くで例と共に示す        |
| エラー               | 何を先に書くか、直し方、主語、禁止語 | エラーは項目名で始め、満たすべき条件を肯定形で書く          |
| 読み込み、完了、失敗 | 動詞の型、感嘆符                     | 進行、完了、失敗は同じ動詞で型を揃える                      |
| 空、完了、失敗       | 文の数、状態と行動の順               | 状態の文言は 2 文以内で、起きたことを先、次の行動を後に書く |
| 確認                 | 問いの型、ボタンの語、辞退側の扱い   | 確認は結果を問いにし、ボタンは結果の語にする                |
| 全部品               | 文字列の持ち方                       | 文言は 1 文を 1 つの文字列で持ち、断片を連結しない          |

「同じ語で呼ぶ」「利用者の語で書く」「回りくどい言い方を直す」「同じ語を 2 度出さない」「断定しない」は単独の Tip にしなかった。
どれもコアの言い換えになり、書式が禁じる形になるからである。

### ボタンの語形

[SmartHR Design System](https://smarthr.design/products/contents/ui-text/app-writing/) はボタンを動詞の終止形とし、サ変動詞は「する」を省く（「追加」「取り消す」）。
[Microsoft Japanese Localization Style Guide](https://aka.ms/japanese-styleguide) はコマンドボタンを体言止め、エラーの本文を敬体とする。
Apple Human Interface Guidelines の日本語版も「カートに追加」「続ける」「次へ」を使う。
「保存する」のように「する」まで書くことを推奨する一次資料は見つからなかった。

面ごとに選ぶ規則のままだと、Button の見本の「続ける」と「削除」は違反になる。
語幹と終止形を 1 つの型と定めれば、日本語の動詞の性質に沿ったまま型が揃う。

### エラー、状態、確認

エラーの規則は [GOV.UK Design System](https://design-system.service.gov.uk/components/error-message/) と [Nielsen Norman Group](https://www.nngroup.com/articles/error-message-guidelines/) に沿う。
どちらも、起きたことと直し方を書き、利用者を責める語を避けるとする。
肯定形で書く規則は、form-inline-validation のレビューが見つけた否定の範囲の読みにくさから足した。

状態の文言を 2 文以内にする値は、Atlassian Design System がメッセージ本文を 1〜2 文とすることに合わせた。
この値は状態の文言に限られるので、コアではなく Tip に置いた。

確認の規則は [Apple Human Interface Guidelines: Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts) と [Nielsen Norman Group](https://www.nngroup.com/articles/confirmation-dialog/) に沿う。
どちらも「はい」「OK」を避け、結果を表す語をボタンに置くとする。
辞退側を貶める文言は [confirmshaming](https://www.deceptive.design/types/confirmshaming) として悪い例に入れた。

### 断片の連結

[Microsoft Globalization](https://learn.microsoft.com/en-us/globalization/internationalization/concatenation) は、断片の連結が語順、複数形、句読点、空白を仮定すると指摘する。
リポジトリには `${layer.title}の索引` のように、日本語の語順を仮定した `aria-label` が既にある。

## 却下した案

- コアから 1 文 50 字を外し、Tip の 2 文以内だけにする: 利用者が 2026-09-22 に継承を選んだ。concise-writing と基準が 1 つになる利点を保つ。
- ボタンを体言止めに統一する: 「続ける」「戻る」を「継続」「前へ」のように漢語へ置き換える場面が出て、利用者の語から離れる。
- ボタンを終止形に統一する（「保存する」）: 語が増えるだけで、予測できる内容は変わらない。一次資料も無い。
- 面ごとに語形を選ぶ規則を保つ: 同じプロダクトの中で面ごとに型が変わり、Button の見本でも混在が起きた。
- 声と調子を別の文書にする: 個人開発のプロダクト群で共通の人格を持つ根拠が無い。
- 画面外の文言まで含める: Tips 8 件に収まらない。
- Catalog の見本帳に固有の 4 件を `module` で残す: 見本帳を作るときの規則で、UX Writing の主題ではない。根拠は [topic-first の採否表](../records/catalog-editorial/rationale/topic-first.md) と [コアの数値 ADR](2026-09-21-guideline-core-values.md) に残っている。

## 出典として使えなかったもの

- Shopify Polaris のコンテンツガイド: 公開が終わり、現行の URL から本文を開けなかった。
- Material Design 3 の Writing と Dialogs: 本文を取得できず、主張を確かめられなかった。
- 翻訳で文言が 30% 伸びるという目安: 一次資料は 2004 年の Microsoft のアーカイブ文書だけだった。

## 採用

利用者が 2026-09-22 に内容を確認し、`status` を `adopted` にすると判断した。
議論で対象範囲、コア、Tips の方向を決め、書き上げた文書を確認したうえでの判断である。

## 影響

- UX Writing の Tips は 15 件から 8 件になった。
- 既存の 15 件はすべて捨てて導き直した。値の項目名、見本の文面、操作説明の非表示、行の折り返しは UX Writing から外れた。
- 送りボタンの規則は、Tip「ボタンは押した後の行動、リンクは行き先の名前で書く」の良い例に吸収した。
- Button の見本の「続ける」と「削除」は新しい規則に適合する。
- 押せない状態の「利用できません」は悪い例として残し、実装は今回変えていない。
- `GuidelinesPage.tsx` の `${layer.title}の索引` は悪い例として残し、実装は今回変えていない。
- 雛形の `- 実験:` のリンク例は `experiments/` を指したままで、今回は直していない。
- 画面文言の表記の文書は未作成である。
