# Design Principles を視覚構成と造形の判断から再設計する

- 状態: Accepted
- 日付: 2026-09-22
- 参照: [Issue #16](https://github.com/salan70/uiux-numa/issues/16)、[Asset composition model](2026-09-20-asset-composition-model.md)、[Guideline の記録形式](../guideline-format.md)
- 対象: [Design Principles](../guidelines/design-four-principles.md)、[Guidelines README](../guidelines/README.md)、[Guideline format](../guideline-format.md)、[ルート README](../../README.md)

## 背景

Design Principles は draft のままで、Catalog に WIP が表示されている。
旧稿は近接・整列・反復・対比を紹介し、余白比、寸法の刻み、文字の段数、基準線の数、画面内の主役数を一律の規則にしていた。
それらの数値や形の制限をすべての画面へ適用できる根拠は示されていない。
一貫性も画面全体の同形化ではなく、意味や役割ごとに判断する必要がある。

利用者は 2026-09-22 に、既存文の推敲や数値調整から始めず、視覚設計で決めることから再設計する仕様を Issue #16 に定めた。
本文の日本語執筆には利用者の指定で agy の Gemini 3.8 Flash High を用いた。
最終稿の採用判断は本 ADR 作成時点では行われていない。

## 決定

- 主題を、UI の可読性と操作性を保ちながら情報の所属・重要度・役割を視覚的に伝える判断とする。
- 近接・整列・反復・対比は手段として扱い、4 原則の説明だけにも全製品共通の作風にも広げない。
- 表示名 Design Principles、slug design-four-principles、作成日 2026-09-20 を維持する。
- Purpose、優先順の Core 4 件、Tips 8 件で構成する。
- Core の順を「読み取りと操作を成立させる」「見た目を意味に対応させる」「同じ役割の表現を繰り返す」「全体の規則を保って細部を整える」とする。
- Core 1 を満たす案の中で Core 2、3、4 の順に判断する。この順序は本稿内に限り、他のガイドラインや知覚法則の強さ順位へ拡張しない。
- Tips 1〜7 を foundation、独自の造形を実寸で調整する Tip 8 を module とする。
- 普遍的な余白比率、数値の刻み、文字階層数、基準線数、画面内の主役数は新設しない。
- 配置と整列に意味を持たせ、関係する要素を意味のある基準へ揃える。
- 意図したずらしは認め、そのずれが伝える関係を明確にする。
- frontmatter の axes は visual hierarchy、consistency、accessibility、localization robustness とする。
- 正本の status は人間が最終稿を確認するまで draft に保つ。
- 外部出典の解説・設計システムの実例・研究報告・WCAG の規範文書を区別し、ローカル判断を普遍則として記さない。

## Core の順序

| 順  | 判断                           | 優先する理由                                                                                           |
| --- | ------------------------------ | ------------------------------------------------------------------------------------------------------ |
| 1   | 読み取りと操作を成立させる     | 読めず操作できない状態では視覚構成の目的を果たせない。文字や内容を揃えるために失わせない。             |
| 2   | 見た目を意味に対応させる       | 所属や重要度の誤読を避け、関係する要素を意味のある基準へ揃える。対称性や均等配置を意味より優先しない。 |
| 3   | 同じ役割の表現を繰り返す       | 役割別の token と表現を再利用し、異なる内容を同形に押し込まない。                                      |
| 4   | 全体の規則を保って細部を整える | 共通の尺度を使いつつ、実寸での光学的な調整と意図した印象を確かめる。                                   |

この順序は情報を読めることと操作できることを最初に守り、その上で意味、役割、一貫した造形を順に確かめるために採る。
他のガイドラインとの衝突を決める共通の優先順位にはしない。

## Tips の導出

既存の見出しや規則を縮めず、視覚設計で決める場面から 8 件を導いた。

| 場面                       | 決めること                              | Tip                                                | 適用       |
| -------------------------- | --------------------------------------- | -------------------------------------------------- | ---------- |
| 入力、表、囲み             | 要素の所属を距離と境界のどちらで示すか  | 余白と境界で所属を明確にする                       | foundation |
| 説明、比較値               | 関係・読む方向・比較単位を伝える基準線  | 読む方向と比較する項目に沿って揃える               | foundation |
| 同じ画面内の情報           | 重要度の差をどの領域で表すか            | 判断するまとまりごとに強調の差を付ける             | foundation |
| 文字                       | 役割と既存の semantic typography の対応 | 文字の役割に既存のスタイルを割り当てる             | foundation |
| 操作、状態                 | 操作可能性と色以外の状態手がかり        | 操作と状態の違いを見た目でも区別する               | foundation |
| 一覧、カード               | 相対位置と可変内容への対応              | 繰り返す項目は読む位置を揃え、内容量には追従させる | foundation |
| 狭い幅、拡大、翻訳         | 再配置後も意味の対応と順を保つ方法      | 幅と文字量が変わっても意味のまとまりを保つ         | foundation |
| 独自のアイコン、図形、題字 | 共通枠内の見かけの重さと位置            | 独自の造形は実寸で見かけを合わせる                 | module     |

Tip 1 は近接だけで所属を判断せず、境界も関係を伝える手段として扱う。
余白の例に Space token を使えても、8px / 24px や 3 倍を必要条件にしない。
表では行・列境界や見出しも所属を伝えるため、余白比だけでは良否を決めない。

Tip 2 は読む方向と比較対象ごとに基準線を選ぶ。
配置と整列で所属、重要度、読む順、比較関係を伝え、関係要素は意味のある局所基準へ揃える。
意図したずらしは禁じず、そのずれ自体が伝える役割を明確にする。
画面全体で 1 本の基準線や基準線の本数上限は求めない。
中央揃えにも中心の基準があり、題字、独立した案内、RTL、意図した非対称構図を認める。
本文を両端揃えにすることも求めない。

Tip 3 は重要度に応じて強さを変え、同時に重要な情報を一律に弱めない。
対等な選択肢には同じ強さを使え、警告を読めなくする強調制限は設けない。
配色とコントラスト条件は Color と Accessibility に委ねる。

Tip 4 は semantic typography の役割を使い、現行 token の size 4 個・semantic 6 個から画面階層の数を制限しない。
行長と文字サイズは token の正本へ委ね、CSS サイズと意味上の見出し階層を混同しない。

Tip 5 は視覚的な操作手がかりと色以外の状態表現を扱う。
状態の意味と通知時期は States & Feedback に、意味の実装は Accessibility に委ねる。
NN/g の調査条件をすべての UI に一般化しない。

Tip 6 は繰り返す項目の相対位置を揃え、長い文言や任意項目に応じた伸長を認める。
段数を固定する [candidate の原則](../principles/block-shape-must-not-vary-by-optional-parts.md) は未検証であり、その効果が確定した根拠として扱わない。

Tip 7 は狭い幅や文字量の変化で組み替えてもラベル、対象、説明、見本の対応を保つ。
WCAG の Reflow は情報と機能を保つ条件であり、二次元の表や図には局所的な例外がある。
適合条件の規範文言は WCAG 2.2 本文に従う。

Tip 8 は独自造形の仕上げに限る。
幾何学的な中心と寸法を出発点とし、実寸で周囲と並べて見かけを調整するが、操作領域やデータの意味は変えない。
ブランドや配布済み素材の制約を優先し、万能な補正値は設けない。

## 根拠と適用範囲

出典の確認は 2026-09-22 に行った。
各資料の主張を Tip の範囲に留め、資料にない数値や普遍的な効果を導かない。

| ID  | 資料の種類と支える内容                                                                                                                                                                                      | 適用上の限界                                 |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| S1  | [NN/g: Proximity](https://www.nngroup.com/articles/gestalt-proximity/) の専門家解説。近さによるまとまり。                                                                                                   | 1.5 倍の数値を裏付けない。                   |
| S2  | [NN/g: Common Region](https://www.nngroup.com/articles/common-region/) の専門家解説。囲みで示す所属と囲み過多の問題。                                                                                       | 装飾や境界の一律禁止を導かない。             |
| S3  | [NN/g: Similarity](https://www.nngroup.com/articles/gestalt-similarity/) の専門家解説。類似する外観から推測する関係や機能。                                                                                 | 全要素を同じ形にする規則にはならない。       |
| S4  | [NN/g: Visual Design Principles](https://www.nngroup.com/articles/principles-visual-design/) の専門家解説。サイズや配置による視覚階層。                                                                     | 記事中の推奨サイズ数を必須上限にしない。     |
| S5  | [Carbon: 2x Grid](https://carbondesignsystem.com/elements/2x-grid/overview/) と [Spacing](https://carbondesignsystem.com/elements/spacing/overview/) の他システムの設計例。基準線、スケール、流動的な配置。 | IBM の token 値を本稿の要件へ移さない。      |
| S6  | [WCAG 2.2: Info and Relationships](https://www.w3.org/WAI/WCAG22/Understanding/info-and-relationships.html) の規格解説。視覚的な関係をプログラムで判別できるか、またはテキストで示す条件。                  | 規範的な適合条件は WCAG 2.2 本文で確かめる。 |
| S7  | [WCAG 2.2: Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) の規格解説。情報と機能を保つ表示の組み替えと二次元配置の例外。                                                                  | 規範的な適合条件は WCAG 2.2 本文で確かめる。 |
| S8  | [WCAG 2.2: Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html) の規格解説。色だけに意味を依存させない条件。                                                                        | 色を一切使わない規則にはならない。           |
| S9  | [NN/g: Flat UI and Uncertainty](https://www.nngroup.com/articles/flat-ui-less-attention-cause-uncertainty/) の特定条件における視線計測研究。操作手がかりが不明瞭な UI の注意と不確実性。                    | すべての UI に同じ効果があるとは扱わない。   |
| S10 | [Carbon: Pictograms — Alignment](https://carbondesignsystem.com/elements/pictograms/usage/#alignment) の他システムの設計例。ピクトグラムの光学的な中央配置。                                                | 全図形に同じ補正を行う規則にはならない。     |

S1〜S4 は専門家による解説、S5 と S10 は特定システムの規約、S9 は条件を伴う研究報告である。
S6〜S8 の Understanding 文書は規格の解説であるため、適合を要求する語句は [WCAG 2.2 本文](https://www.w3.org/TR/WCAG22/) と照合する。
本文を確認できない書籍の商品ページは、新しい規則の根拠にしない。

## 却下した案

- 既存文の推敲や数値だけの調整から始める: 見出し順や初期の偏りを残すため、判断する場面から Core と Tips を導く。
- 近接・整列・反復・対比の紹介だけにする: 所属、重要度、操作性、可変内容の判断を補えない。
- 白黒、角丸、特定書体、装飾禁止、全画面の同形化を foundation にする: Catalog の作風を他製品へ強制する根拠がない。
- 余白差を 1.5 倍以上とする: 出典と測定条件がなく、表や囲みを含む一般条件にできない。
- 余白を 4px または 8px の倍数だけにする: 現行 Space には 2px と 6px があり、一律の刻みを必要条件にできない。
- 文字階層を 4〜6 段にする: primitive token、semantic token、画面内の役割数を混同する。
- 基準線を 2 本までにし、全要素を 1 本の画面全体基準へ揃え、中央揃えを避ける: 多列の表、役割別の基準、中央配置、RTL、意図したずれを理由なく排除する。
- 全部品で角丸と線幅を揃える: Radius には役割別の値があり、OS 標準部品も使うため、役割ごとの一貫性を採る。
- 違いを常に強くする、または主役を 1 つにする: 同時に重要なエラーや対等な選択肢まで弱めるおそれがある。
- 近接・整列・反復・対比を常に全て使う: 全ての手段を使うことではなく、伝える関係が成立することを判断する。
- 黄金比、フィボナッチ数列、8px グリッドを美しさの保証にする: これらの値だけで目的に合う造形を保証できない。

## 関連文書への提案

- Color の「有彩色は狭く」「面は無彩色」を全製品の foundation とする根拠は弱いため、プロダクトが選ぶ作風として扱う方向を別途検討する。
- Typography token の行長上限を外す規則には、見た目と読みやすさの衝突があるため、Catalog の現状を変えず適用範囲の再検討を提案する。
- state-changes-must-not-move-layout.md は色だけで状態を示すように読める題名を、操作位置の安定と複数の手がかりに合わせて見直す余地がある。
- guideline-format.md と Guidelines README の foundation の説明は Asset model の既定の土台と上書き理由に揃える。

これらの提案は各正本の判断を変更しない。
対象文書の全面改稿や token 値の変更は本 ADR に含めない。

## 影響

- Design Principles の既存 Core と Tips を全面的に置き換える。
- Catalog は正本を自動読込し、既存表示と WIP 判定を継続して使う。
- Information Architecture、UX Writing、Japanese Notation との境界を保つ。
- Typography、Space、Radius の token 値と candidate の status は変更しない。
- 既存 ADR は履歴として保持し、この ADR が置き換える判断だけを明示する。

## 検証

- Guideline parser が 3 つの H2、Core と Tips の構造、Core 参照、許可された list key を受理することを確認する。
- 正本・token・principle・Skill への内部リンクが Catalog から意図したファイルへ解決することを確認する。
- 原典とリンク先を開き、出典の主張が Tip の内容を支える範囲に留まることを照合する。
- Nix 環境で just catalog-check、just catalog-test、just catalog-build、just lint を実行する。
- Catalog を 390 / 1280 CSS px、light / dark で確認し、Purpose・Core・Tips・目次・good / bad・例外・WIP を見る。
- 390 / 1280 のスクリーンショットを確認記録として残す。画面の再デザインは行わない。
- 人間が本文を採用した場合だけ status を adopted にして一覧を更新し、WIP が消えることを確認する。

## 採用判断

ガイドライン本文の採否は保留である。
利用者が最終稿を確認し、採用を決めた場合は判断者・日付・理由をここへ記録する。
