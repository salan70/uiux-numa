# interaction / motion レビュー: 入力フォームの inline validation

- 観点: interaction / motion
- 対象: on-blur、on-submit、realtime、hybrid
- 入力: README、variants/、previews/、docs/evaluation/axes.md
- 担当した軸: feedback quality、interaction clarity、perceived performance

## 判定

| 軸                    | on-blur                                                                                                                                                  | on-submit                                                                    | realtime                                                                                                           | hybrid                                                                                                                                                     |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| feedback quality      | 許容: 離脱時の指摘は入力を妨げないが、修正の完了は次の離脱まで伝わらない                                                                                 | 許容: 要約とフォーカス移動で結果は伝わるが、修正の完了は再送信まで伝わらない | 許容: 修正の完了は入力中に即座に伝わるが、完了文言に成功色がなく、成功表示の量も増える                             | 許容: 要約で結果と件数が伝わり、修正の完了は再送信なしで離脱時に伝わる。入力中は解消済みの文言が残る                                                       |
| interaction clarity   | 保留: 入力中は解消済みのエラーが残る。修正の直後に登録するを押すと文言が消えてボタンが動き、クリックが外れる可能性がある。実操作の録画があれば判定できる | 許容: 要約から項目への移動は明確だが、修正後も再送信まで無効の表示が残る     | 保留: 表示名の初回離脱で文言が挿入され、登録するの初回クリックが外れる可能性がある。実操作の録画があれば判定できる | 保留: 修正の直後に登録するを押すと、文言と要約の行が消えてボタンが 52px 以上動く。有効な入力でクリックが外れる可能性がある。実操作の録画があれば判定できる |
| perceived performance | 許容: 応答は即時だが、修正の確認には離脱が 1 回必要                                                                                                      | 許容: 応答は即時だが、修正の確認には再送信と要約からの往復が必要             | 良い: 修正の確認が入力中に返り、往復がない。初回クリックの取りこぼしが再現すれば見直す                             | 許容: 応答は即時で再送信の往復は要らないが、誤りの把握に送信、修正の確認に離脱が要る                                                                       |

## 観察

### on-blur

- 入力中は値だけ更新し、エラー文言は触らない（variants/on-blur/index.tsx 61-64 行）。
- そのため修正が済んでも、離脱するまで赤い枠と文言が残る（同 66-69 行）。
- 離脱のたびに再検証するので、離脱すれば解消は分かる（同 68 行）。
- 未入力のまま離脱すると、その場で「未入力です」が出る（同 33、37、44 行）。
- 入力せずに通過しただけの項目にもエラーが出る点は、指摘の時期が早い。
- 送信時は全項目を検証し、最初の無効項目へフォーカスを移す（同 74-85 行）。
- flushSync で文言を描画してからフォーカスを移すため、参照先が揃う（同 82-83 行）。
- 要約はない。3 項目が 1 画面に収まるため、赤い枠で無効項目を見渡せる（on-blur-error.png）。
- on-blur-error.png にはフォーカスリングがない。送信後のフォーカス位置は preview から確認できない。
- 成功時はフォームを完了文言に置き換える（同 87、90-98 行）。フォーカスの移動先は指定しない。
- 完了文言は成功色の太字になる（on-blur-success.png、styles.css 64-68 行）。フォーム全体が消えるので、完了は見て分かる。
- transition と animation はない（variants/on-blur/styles.css）。状態の変化は瞬時に切り替わる。
- 文言の領域を確保していない（styles.css 15-19、40-43 行）。離脱時にエラーが出ると、送信ボタンが下へ動く。
- 表示名が無効なまま登録するをクリックすると、押下時の離脱で文言が挿入される。ボタンは約 28px 動く。
- ボタンの高さは 40px なので、クリックが外れる可能性がある。ただし表示名のエラーは見えるため、次の操作は分かる。
- hybrid との比較で、文言が消える側にも同じ経路があると分かった。
- 直した項目から登録するを押すと、離脱で文言が消える（index.tsx 68、126-130 行）。
- ボタンは約 28px 上へ動き、中央付近のクリックは外れる見込みである。
- この経路は有効な入力で起き、外れると文言が消えるだけで送信は起きない。
- realtime と同じ種類の経路である。
- そのため interaction clarity は許容から保留に改めた。
- この取りこぼしはコードから読んだ推測であり、実操作で確認したい。

### on-submit

- 入力中も離脱時も検証しない（variants/on-submit/index.tsx 64 行）。送信時にだけ全項目を検証する（同 86-95 行）。
- 送信までは何も起きないので、入力の流れは妨げられない。
- 送信後はフォーム先頭に要約を挿入し、要約へフォーカスを移す（同 79-84、119-140 行）。
- on-submit-error.png の要約にはフォーカスリングがあり、移動を確認できる。
- 見出しに件数、リストに各項目へのリンクがあり、修正の見通しが立つ（同 127-137 行）。
- リンクは既定の遷移を止め、対象の入力欄へフォーカスを移す（同 97-101 行）。
- 要約の挿入で全項目が約 130px 下へ動く（on-submit-error.png）。フォーカスが要約へ移るため、視線は追える。
- エラーは送信時にだけ更新する（同 64-69 行）。修正しても再送信まで赤い枠と文言が残る（同 159-164 行）。
- 要約の件数も再送信まで減らないので、修正が足りているかは分からない。
- 再送信のたびに要約へフォーカスが戻る（同 65-66、80-84 行）。要約、リンク、入力欄の往復が繰り返される。
- 成功時はフォームを完了文言に置き換える（同 103-111 行）。フォーカスの移動先は指定しない。
- 完了文言は成功色の太字になる（on-submit-success.png、styles.css 88-92 行）。フォーム全体が消えるので、完了は見て分かる。
- transition と animation はない（variants/on-submit/styles.css）。要約の出現も瞬時に切り替わる。
- 押下時に文言が挿入されないため、送信ボタンのクリックが外れる経路はない。

### realtime

- 各項目は初回の離脱まで検証しない（variants/realtime/index.tsx 89-94 行）。以降は入力のたびに検証する（同 79-87、132-134 行）。
- 初回の通過では入力を妨げず、修正に戻ったときは即座に結果が返る。
- 離脱後は常にエラーか「問題ありません」を表示する（同 134、152-168 行）。文言の行は空にならない。
- 修正が済んだ瞬間に赤から緑へ切り替わり、解消が分かる。realtime-error.png のメールアドレスがこの状態である。
- 文言を key にして要素を作り直す（同 155 行）。切り替えのたびに 150ms のフェードを再生する（styles.css 47-51、95-105 行）。
- フェードは表示側だけで、消える側の動きはない。150ms は待ちと感じない長さである。
- 色と文言の変化だけでも意味は伝わり、フェードは変化の瞬間へ目を向けさせる補助になる。
- 枠線の色も 150ms で遷移する（styles.css 34 行）。
- prefers-reduced-motion では transition と animation を無効にする（styles.css 108-116 行）。動きがなくても色と文言で意味は保たれる。
- 文言が同じ間は key が変わらず、フェードは再生されない（同 155 行）。1 文字ごとに点滅することはない。
- 入力せずに通過した項目にも「入力してください」が出る（同 28 行）。以降は 1 文字ごとに検証し、文言が変わる（同 83-86 行）。
- 送信時は全項目を検証済みにし、最初の無効項目へフォーカスを移す（同 96-116 行）。
- 要約はないが、送信後は全項目に文言が出るので、無効項目は赤い枠と文言で見渡せる。
- 成功時はフォームを完了文言に置き換える（同 118-124 行）。className がなく、成功色にならない（realtime-success.png）。
- 完了文言は黒の通常文字で、他 2 variant の緑の太字と比べると成功を伝える手段が弱い。
- 成功文言は `@` を含むだけで出る（同 29 行）。`n@` のような入力途中でも「問題ありません」になる。
- 表示名の初回離脱では必ず文言が挿入される。送信ボタンは約 25px 下へ動く（styles.css 15-19、47-51 行）。ボタンの高さは 40px である。
- 表示名に入力してそのまま登録するをクリックすると、押下時に離脱が起きる。ボタンが動くため、クリックが外れる可能性がある。
- この経路は有効な入力でも起き、外れると緑の文言だけが出て送信は起きない。
- キーボードでは Tab でフォーカスが移るため、この影響を受けない。
- この取りこぼしはコードから読んだ推測であり、実操作の録画で確認したい。

### hybrid

- 送信前は離脱でも検証しない（variants/hybrid/index.tsx 105 行）。
- 入力中は値だけを更新し、文言と要約に触らない（同 98-101 行）。
- 送信前は通過した項目にも文言が出ず、入力の流れを妨げない（hybrid-initial.png）。
- 規則に合わない入力に気づくのは送信時で、on-submit と同じ時期である。
- 送信前は表示が変わらないため、登録するの初回クリックは外れない。
- realtime の表示名の初回離脱で起きる経路はない。
- 送信時は全項目を検証し、要約と各項目の文言を出す（同 118-128 行）。
- 要約は描画後にフォーカスを受ける（同 84-89 行）。
- hybrid-error.png の要約にはリングがあり、移動を確認できる。
- 要約の挿入で全項目が約 130px 下へ動く（hybrid-error.png）。
- フォーカスが要約へ移るため、視線は追える。
- 要約のリンクは遷移を止め、入力欄へフォーカスを移す（同 130-135 行）。
- 送信後は、離脱した項目だけを再検証する（同 103-116 行）。
- 解消は離脱の時点で、文言の消失と枠の色の戻りで伝わる（同 198-205 行）。
- 要約の件数も同時に減り、残りの件数が再送信なしで分かる（同 147、161 行）。
- 入力中は更新しないため、離脱までは on-blur と同じく解消済みの文言が残る。
- 項目ごとの成功表示はなく、解消は表示が消えることでだけ伝わる。
- 離脱による更新ではフォーカスを動かさない（同 84 行）。
- 要約が残ったまま再送信すると、要約へフォーカスが戻る（同 85-89、127 行）。
- 件数を見て直し終えてから送信できるため、on-submit より再送信の往復は減る。
- 要約と文言の領域は確保していない（styles.css 16-20、65-68 行）。
- 1 件を解消すると、要約の 1 行（約 24px）と文言の行（約 28px）が消える。
- 解消した項目より下の要素と登録するは、52px 以上上へ動く。
- 最後の 1 件を解消すると要約ごと消え、登録するは約 134px 上へ動く。
- 0 件の後に誤りが出ると、要約はフォーカスを伴わず再挿入される（index.tsx 152 行）。
- このとき登録するは約 134px 下へ動き、要約は原因の項目から離れた先頭に出る。
- 直した項目から登録するを直接押すと、押下時の離脱でこの移動が起きる。
- 移動は 52px 以上で、ボタンの高さ約 42px を超える（hybrid-error.png）。
- この経路は有効な入力で起き、外れると要約と文言が消えるだけで送信は起きない。
- 要約と文言が消える変化を、送信の応答と取り違える可能性がある。
- realtime と違い初回に限らず、修正の直後に登録するを押すたびに起きうる。
- 要約のリンクにも同じ経路がある（index.tsx 147、163-175 行）。
- 上の項目を直して次のリンクを押すと、押下時に上の行が消えてリンクがずれる。
- ずれは 1 行分（約 24px）以上で、外れると入力欄へフォーカスが移らない。
- 要約は項目の順に並ぶため、上から順に直すとこの経路を通る（index.tsx 19-23 行）。
- Tab での移動と、入力欄で Enter を押す送信は、この影響を受けない。
- 文言の行の高さを確保しても、要約の行の増減で登録するは動く。
- この取りこぼしはコードから読んだ推測であり、実操作の録画で確認したい。
- 成功時は完了文言に置き換え、描画後にフォーカスを移す（index.tsx 91-96 行）。
- hybrid-success.png では、完了文言が緑の太字でリングを伴う。
- フォーカスが body に落ちず、キーボード操作の起点が完了文言に定まる。
- 完了文言のリングはマウス操作でも出る（styles.css 98-103 行）。
- 操作できない文に枠が付くため、押せる要素に見える可能性がある。
- transition と animation は使わない（styles.css 1 行）。
- 要約の出現、件数の更新、消失は瞬時に切り替わる。
- 意味は文言の有無と枠の色で伝わり、reduced motion に依存しない。
- 52px から 134px の移動も瞬時で、移動の前後をつなぐ手がかりはない。
- 高さの遷移を付けても、押下中に登録するが動く点は変わらない。

## 論点

- 登録するを押したクリックが外れるかを、Chrome と Safari の実操作で録画して確認したい。
  経路は 2 種類ある。
  realtime は、表示名の初回離脱で文言が挿入される経路である。
  on-blur と hybrid は、修正の直後の離脱で文言が消える経路である。
  hybrid は初回クリックの経路を持たない。
  hybrid は要約の行も消えるため移動が大きく、要約のリンクにも同じ経路がある。
  interaction clarity の保留 3 件は、この結果で判定する。
  再現しなければ許容、再現すれば課題ありとする。
- hybrid 以外は成功時にフォームが消え、フォーカスが body に落ちる。
  完了文言へフォーカスを移すかは accessibility と合わせて判断したい。
  hybrid で解消: 完了文言へ移す（hybrid/index.tsx 91-96 行）。
  ただしリングはマウス操作でも出る（hybrid/styles.css 98-103 行）。
  操作できない文に枠を出してよいかは、designer と確認したい。
- realtime の完了文言に成功色がない。Brief の制約と異なるため、designer と implementation で確認したい。
- realtime の文言は 0.875rem である（realtime/styles.css 49 行）。他 variant の 16px と異なる。担当外だが、designer の consistency で確認したい。
- realtime だけに動きがある。
  hybrid は動きを使わず、要約の増減で最大約 134px の移動が瞬時に起きる。
  motion appropriateness は評価軸に選ばれていない。
  追加するかは担当者に委ねる。
- hybrid の要約を、離脱のたびに更新するか、送信時だけ更新するかを判断したい。
  離脱での更新は残りの件数を伝えるが、行の増減で登録するとリンクが動く。
  0 件の後に誤りが出ると、要約はフォーカスを伴わずに再び出る。
- email の規則が `@` を含むだけのため、realtime では入力途中でも成功文言が出る。成功表示を採用するなら、規則の粒度を見直すか判断したい。
- realtime は空白だけの入力を有効とみなす（realtime/index.tsx 28、41 行）。on-blur と on-submit は trim する（on-blur/index.tsx 30 行、on-submit/index.tsx 36 行）。表示名の文字数の数え方も異なる。担当外だが、implementation で確認したい。
- on-submit だけ autoComplete を指定している（on-submit/index.tsx 19-21、156 行）。
  変えた軸ではないため、implementation で確認したい。
  hybrid で解消: 指定がある（hybrid/index.tsx 20-22、193 行）。
  on-blur と realtime には残る。
- 疑似送信のため、perceived performance は待ち時間で差が出ない。修正までの往復回数だけで判定した。送信中の状態を比較するなら、別の Experiment が必要になる。
