# Guideline の記録形式

1 主題を `docs/guidelines/<slug>.md` に閉じ、YAML frontmatter と 3 つの節で書く。
雛形は [docs/templates/guideline/guideline.md](templates/guideline/guideline.md) にある。
基準となる見本は [states-and-feedback.md](guidelines/states-and-feedback.md) である。迷ったらこの文書に合わせる。

この文書は書き手と AI エージェント向けの書式の正本である。
読み手向けの説明は [docs/guidelines/README.md](guidelines/README.md) に置く。
書式の量と読み方の量が釣り合わないため、1 文書に混ぜず分けた。

書式の判断は [方針の書式 ADR](decisions/2026-09-20-guideline-format.md) と
[対比の対 ADR](decisions/2026-09-21-catalog-guideline-contrast-pair.md) に残す。
Catalog に載せる理由と範囲は [方針を二次情報として載せる ADR](decisions/2026-09-20-catalog-guidelines.md) に残す。

## ディレクトリ構成

```text
docs/guidelines/
├── README.md      # 読み手向けの入口。ガイドラインではない
└── <slug>.md      # ガイドライン 1 主題
```

- 1 文書 1 主題にする。主題が 2 つに割れたら文書を分ける。
- slug は小文字の英数字とハイフンだけの kebab-case にする（例: `states-and-feedback`）。
- 日付 prefix を付けない。作成日は frontmatter の `created` に持つ。
- `README.md` は解析器が読み飛ばす。ここにガイドラインの内容を書かない。

## frontmatter

```yaml
---
title: <英語の文書名>
summary: <1〜2 文の要約>
status: draft
axes:
  - <docs/evaluation/axes.md の 17 軸から選択>
created: YYYY-MM-DD
updated: YYYY-MM-DD
---
```

| キー      | 必須 | 内容                                                                    |
| --------- | ---- | ----------------------------------------------------------------------- |
| `title`   | 必須 | Catalog の表示名。英語にする。本文は日本語で書く                        |
| `summary` | 必須 | 文書の概要を兼ねる。Catalog では題字の直下に出る                        |
| `status`  | 必須 | `draft` か `adopted`。新規は `draft` から始める                         |
| `axes`    | 必須 | [評価軸](evaluation/axes.md)の 17 軸から 1 つ以上。軸名は完全一致で書く |
| `created` | 必須 | 作成日                                                                  |
| `updated` | 必須 | 最終更新日                                                              |

`created` と `updated` は機械検査の対象外である。書き忘れても build は落ちないので、更新時に手で直す。

## 本文の節

`## 目的` → `## コア` → `## Tips` の 3 節だけを、この順で置く。
これ以外の H2 を置くと build が落ちる。節を欠いても落ちる。

| 節   | 書くこと                                                                 |
| ---- | ------------------------------------------------------------------------ |
| 目的 | その主題で目指す状態。2〜3 文。他の文書との境界は要るときだけ 1 文で書く |
| コア | 主題の思想。3〜5 件                                                      |
| Tips | 具体的な場面の規則。8 件までを目安にする                                 |

コアと Tips は書式が違う。
コアは何を優先するかを決め、Tips は場面ごとに何をするかを決める。

## コアの項目

各コアは第 3 レベル見出し（`###`）と本文 1〜3 文で書く。

```markdown
### 配置を動かさない

状態の変化で周囲の要素を動かさない。
表現の豊かさより、押し先が変わらないことを優先する。
```

- 見出し: 短い名詞句か短文にする。Tips がこの見出しで引くので、後から変えると Tips も直る。
- 本文: 目指す状態を 1 文で書き、「A より B を優先する」の形でトレードオフを 1 文で締める。
- 並び順: コア同士が衝突したときの優先順位を表す。上が勝つ。
- 箇条書きを書かない。具体例、値、出典を持たせない。書きたくなったら Tips へ送る。

部品、画面、操作の名前や具体的な値が出るものは Tips に置く。

## Tips の項目

各 Tips は第 3 レベル見出し（`###`）で始め、`意図と根拠:` の段と `- key: value` の並びを続ける。

```markdown
### 内容が変わる場所は領域を先に確保する

意図と根拠: 文字数の増減やエラー文の出し入れで寸法が変わると、次の押し先がずれる。
form-inline-validation では、エラー文の消去で送信ボタンが 28px 動いた。

- 適用: foundation
- コア: 配置を動かさない
- 良い例: 数字の表示幅を最大値で固定し、エラー文の行を `min-height` で予約する。
- 悪い例: エラー文の要素ごと取り除き、下の送信ボタンをせり上がらせる。
- 例外: 画面端まで flex で広がる流動的なグリッド配置。
- 実験: [form-inline-validation](../../experiments/form-inline-validation/README.md)
```

| 項目          | 必須 | 内容                                                                              |
| ------------- | ---- | --------------------------------------------------------------------------------- |
| 見出し        | 必須 | 規則の内容を行動で示す                                                            |
| `意図と根拠:` | 必須 | なぜその規則が必要かを 1〜2 文。コアの思想は繰り返さない。複数行に続けてよい      |
| `- 適用:`     | 必須 | `foundation` か `module`                                                          |
| `- コア:`     | 必須 | 関連するコアの見出しと完全一致。複数あれば行を繰り返す                            |
| `- 良い例:`   | 必須 | 推奨する表現や実装                                                                |
| `- 悪い例:`   | 必須 | 避けるべき表現や実装                                                              |
| `- 例外:`     | 任意 | 規則が効かない場面                                                                |
| `- 実験:`     | 任意 | リポジトリ内の出どころへの相対リンク 1 つ。Experiment、ADR、原則候補、Skill、実装 |
| `- 出典:`     | 任意 | 外部文献や WCAG 達成基準へのリンク 1 つ。規則がその文献の主張であるときに書く     |

表に無い箇条書きの項目を書くと build が落ちる。
`意図と根拠:` は箇条書きにしない。行頭に `-` を付けると未知の項目として落ちる。

Tips は必ずコアに結び付ける。コアの言い換えになる Tips は置かない。
`foundation` を先、`module` を後に並べる。
適用の語は [asset-model](asset-model.md) の role と揃える。

| 値           | 意味                                       |
| ------------ | ------------------------------------------ |
| `foundation` | すべてのプロジェクトで守る                 |
| `module`     | その主題を重視するプロジェクトで選んで守る |

## 値の中で使える記法

`apps/catalog/src/content/guidelines.ts` の `renderInline` が解釈するのは次の 3 つだけである。

- `` `code` ``
- `[text](url)`
- `**強調**`

見出し、箇条書き、表、画像は値の中に書かない。
相対リンクは GitHub の blob URL へ解決されるので、リポジトリのルートからの相対パスで書く。
`- 実験:` と `- 出典:` は Markdown リンクでなければならない。素のテキストや素の URL は落ちる。

## 機械検査

解析器は `apps/catalog/src/content/guidelines.ts` にある。
不整合があれば throw して build を落とす。既定値で埋めない。

```bash
nix develop -c just catalog-test    # 解析器の単体テスト
nix develop -c just catalog-build   # 全文書の読み込みと検証
```

落ちる条件は次のとおり。

| 対象        | 条件                                                                  |
| ----------- | --------------------------------------------------------------------- |
| frontmatter | `title` か `summary` が空。`status` が `draft` / `adopted` 以外       |
| frontmatter | `axes` が空。17 軸に無い軸名がある                                    |
| 節          | `目的` / `コア` / `Tips` 以外の H2 がある。3 節のいずれかが無い       |
| 目的        | 本文が空                                                              |
| コア        | 1 件も無い。本文が空。箇条書きが混ざっている                          |
| Tips        | 1 件も無い                                                            |
| Tips        | `意図と根拠` / `良い例` / `悪い例` / `適用` / `コア` のいずれかが無い |
| Tips        | `適用` が `foundation` / `module` 以外                                |
| Tips        | `コア` が `## コア` に無い見出しを指す                                |
| Tips        | 上の表に無い箇条書きの項目がある                                      |
| Tips        | `実験` か `出典` が Markdown リンクでない                             |

雛形はプレースホルダのまま検査を通らない。
`- コア:` が `## コア` の見出しと一致しないためである。値を埋めてから検査する。

## 画面に出るもの、出ないもの

正本は記録であり、Catalog は読む導線である。両者は一致しない。
書いたのに画面へ出ない項目があるので、出ないことを理由に省かない。

| 項目                                | 画面   | 備考                                       |
| ----------------------------------- | ------ | ------------------------------------------ |
| `title`                             | 出る   | 題字                                       |
| `summary`                           | 出る   | 題字の直下                                 |
| `## 目的`                           | 出る   | `Purpose`                                  |
| `## コア`                           | 出る   | `Core`。番号は優先順位                     |
| Tips の見出しと `適用`              | 出る   | 1 段目。適用は見出しの横                   |
| Tips の `意図と根拠`                | 出る   | 2 段目                                     |
| Tips の `良い例` と `悪い例`        | 出る   | 3 段目。good を左、bad を右に並べる        |
| Tips の `例外`                      | 出る   | 4 段目                                     |
| `status` `axes` `created` `updated` | 出ない | 正本の管理情報                             |
| Tips の `コア`                      | 出ない | 規則を使う側の判断を変えないため           |
| Tips の `実験` と `出典`            | 出ない | 判断の記録なので正本に残し、導線に挟まない |

節の見出しは画面では英語（Purpose / Core / Tips / Index）になる。正本の節名は日本語のままにする。
出さない判断は [対比の対 ADR](decisions/2026-09-21-catalog-guideline-contrast-pair.md) に残す。

## 文書を足す手順

1. [雛形](templates/guideline/guideline.md)を `docs/guidelines/<slug>.md` へ複製する。
2. frontmatter と本文を書く。コアを先に決め、Tips は必ずいずれかのコアへ結び付ける。
3. `apps/catalog/src/content/guidelines.ts` の `GUIDELINE_ORDER` へ slug を足す。
   落としても build は通り、一覧の末尾へ並ぶだけなので気づきにくい。
4. [docs/guidelines/README.md](guidelines/README.md) の文書一覧へ行を足す。
5. `nix develop -c just catalog-test` と `nix develop -c just lint` を通す。
6. 人間が内容を確認し、`status` を `adopted` にする。判断者、判断日、理由は ADR に残す。

改訂するときは、変更の理由と根拠を先に明らかにする。
外部文献は原典を開き、URL が生きていること、その主張が規則と一致することを確かめる。
リポジトリ内の実験で確かめた知見があれば `- 実験:` で出どころに結び付ける。
