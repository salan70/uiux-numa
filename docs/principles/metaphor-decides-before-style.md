## 仮説

図が何を指すかは、描き方（線か塗りか、端点、色数）ではなく比喩で決まる。
比喩が意味に届かない場合、描き方を変えても届くようにはならない。
したがって比喩の候補を先に複数描いて比べ、決まってから描き方を選ぶ。

## 適用条件

- 成果物: 意味を伝える図全般。アイコン、ロゴ、挿絵。
- 特に、既知の対応が弱い概念（API、テスト、AI、抽象的な行為）を表すとき。
- 既知の対応が強い概念（封筒とメール、虫眼鏡と検索）では、比喩の選択に迷いが少ないため効果が薄い。

## 必要な値

この候補の手順であり、普遍の正解ではない。

1. 概念ごとに、既知の対応があるかを先に判断する。5 秒で比喩が思いつかなければ、対応は弱い。
2. 対応が弱い概念では、比喩の候補を 2〜3 個、下書きで描く。描き方はこの段階で揃えなくてよい。
3. 実利用の最小サイズで描画し、意味が読めるかを比べる。読めない候補をここで落とす。
4. 比喩が決まってから描き方を選ぶ。
5. どの比喩でも意味に届かない場合は、ラベル併記を前提とするか、その概念を図にすることを諦める。

## 作例

`experiments/class-tech-icons` の `api` と `test` が悪い例である。
4 案が異なる描き方（丸い線画、角張った線画、塗り、2 色）で同じ比喩の系統を選び、4 案とも意味に届かなかった。
`api` の往復矢印から出るのは「交換」「同期」「送受信」までで、「API」には届かない。
`test` はフラスコでもチェック済みの検査票でも、「実験」か「完了」が先に読まれた。

良い例は同じ Experiment の `terminal` と `database` である。
4 案が異なる描き方で描いても、意味は 4 案とも読めた。既知の対応が強いためである。

preview は `experiments/class-tech-icons/previews/compare-final-24.png`。
評価の記録は `experiments/class-tech-icons/evaluation/ux-product.md`。

## 例外

- 描き方が意味を壊す場合はある。`class-tech-icons` の `solid` では、`branch` が 20px で塊になり構造が消えた。比喩は同じでも、塗りの語彙が細部を消した。この原則は「描き方は意味を良くしない」であって、「描き方は意味を壊さない」ではない。
- ラベルを常時併記する場面では、比喩が弱くても実害が小さい。目印としての区別さえつけばよい。

## 検証結果

- `class-tech-icons`（2026-09-19）: 4 案 × 8 個で、意味に届かなかったのは `api` と `test` の 2 個。どちらも 4 案すべてで届かなかった。描き方による差は出なかった。
- `class-doc-logo` と `class-chapter-illustration`（2026-09-19）: 比喩の方向を変えた 4 案と 2 案が、すべて利用者に却下された。却下の理由に「比喩が合わない」が挙がった。比喩が判断を分けることの傍証になる。
- 未検証: 手順 2〜3（比喩の候補を先に描いて比べる）を実際に運用した場合の効果。`class-tech-icons` では一部の案が `ai` と `api` で候補を比べており、その案でも `api` は届かなかった。
- 未検証: 意味の読み取りは agent による推測であり、ユーザーテストではない。
