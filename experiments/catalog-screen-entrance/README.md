## Problem

Catalog の画面が表示されるとき、見出しの立ち上がりで画面の印象を整える。
現状は本文が 1 フレームで差し替わり、動きが無い。
利用者は 2026-09-23 に、画面表示時の動きを検討して Catalog に加えることを求めた。
1 巡目の短い動きを見て、利用者は「スタイリッシュなサイトでよくある感じ」にしたいと判断した。

## Target

Catalog の Works と Guidelines をサイドバーから行き来して成果物を見比べる人を対象にする。
1 回の閲覧で画面の表示は数十回起きる。

## Scope / Domains

対象は animation / motion、interaction、accessibility とする。
動かすのは画面の見出しと、その下のリード 1 段だけにする。
variant で変える軸は、見出しを分ける単位（行 / 語 / 文字）と、現れ方（窓からせり上がる / 焦点が合う / 波で立ち上がる）の組である。

crafting-motion の手順に沿った判断は次のとおり。

- 動かすか: 頻度は「1 日に数十回」に当たり、表の出発点は「ごく短い変化か、なし」である。1 巡目はこれに従って 120〜200ms にしたが、利用者は動きの感じが分からないと判断した。2 巡目は出発点を外し、見出しの印象を目的に 600〜900ms の動きを試す。
- 頻度の代償を抑える方法: 動かすのは見出しとリードだけにし、本文の区画は動かさない。動きの途中でも操作は受け付け、何も待たせない。見出しは移動の大半を前半 3 割で終える曲線にし、動いている間も読める。
- 目的: 画面の印象を整える。crafting-motion の分類では「喜び」に近いが、稀な操作ではない。利用者の判断を根拠に置く。
- 手段: CSS animation。表示のたびに要素を描き直し、マウント時に一度だけ再生する。`@starting-style` と transition でも書けるが、transition を常設すると入場以外で `opacity` や `transform` が変わったときも動く。animation は入場の一度だけに効く。
- 属性: `transform` と `opacity` を基本にする。`blur-focus` だけは `filter` を使う。焦点が合う感じはぼかしでしか出せず、この案の軸そのものだからである。

動かさないもの:

- サイドバー: 画面をまたいで同じ場所に留まることが、どこにいるかの手がかりになる。
- 本文の区画: 読みたい内容が動きの後ろで待たされないようにする。
- 配色のダイアログの開閉: `App.tsx` の `screenKey` は配色の詳細を一覧と同じ画面として扱う。画面の表示ではないので再生しない。

## Constraints

- React + TypeScript と CSS で実装し、追加依存を入れない。
- 既存の motion token で足りる値はそれを使う。足りない値は variant 内の局所値にし、token にするのは採用後にする（`tokens/motion/README.md` の追加規則「公開 Catalog に実利用がある値だけを追加する」）。
- `prefers-reduced-motion: reduce` では移動、ぼかし、順番のずれを止め、透明度の変化だけを `duration.state` と `easing.standard` で残す。
- 分けた文字を 1 つずつ読み上げさせない。見出しの全文を `aria-label` に持たせ、分けた span は `aria-hidden` にする。
- 入力の種類で動きを変えない。キーボードで移っても画面の表示は同じで、頻度も同じだからである。crafting-motion の「キーボード起点なら動かさない」は仮説であり、ここでは外す。
- 標本は Catalog の配色と light / dark を読む。

## Hypothesis

見出しを分けて順に出すと、短い動きでは伝わらなかった「動いた」という印象が伝わる。
分ける単位が大きいほど落ち着き、小さいほど華やかになる。
どの単位なら数十回見ても煩わしくないかを比べる。

## Variants

| id             | 仮説                                                               | 変えた軸                                              | 実装                     |
| -------------- | ------------------------------------------------------------------ | ----------------------------------------------------- | ------------------------ |
| `line-mask`    | 行を窓にして下からせり上げると、編集誌のように締まって見える       | 行ごとに窓からせり上がる。800ms、行の間隔 100ms       | `variants/line-mask/`    |
| `blur-focus`   | 語ごとにぼかしから焦点を合わせると、柔らかく上質に見える           | 語ごとにぼかしから焦点が合う。900ms、語の間隔 80ms    | `variants/blur-focus/`   |
| `char-stagger` | 1 文字ずつ波のように立ち上げると、最も動きが分かり、華やかに見える | 1 文字ずつ波で立ち上がる。600ms、文字の間隔 30ms      | `variants/char-stagger/` |

値と根拠:

| 値                               | 使う案                        | 根拠                                                                                        |
| -------------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------- |
| 800ms                            | `line-mask`                   | 文字が窓を通る道のりを目で追える長さ。1 巡目の 120〜200ms では動きの感じが伝わらなかった     |
| 900ms                            | `blur-focus`                  | ぼかしが解ける過程は移動より追いにくく、`line-mask` より少し長くしないと焦点の変化が読めない |
| 600ms                            | `char-stagger`                | 1 文字は小さく道のりも 0.5em と短いので、行や語より短くても動きが見える                      |
| `cubic-bezier(0.16, 1, 0.3, 1)`  | `line-mask`、`char-stagger`   | 立ち上がりが速く長く減速する expo 系の ease-out。移動の大半を前半 3 割で終え、早く読める     |
| `cubic-bezier(0.22, 1, 0.36, 1)` | `blur-focus`                  | expo 系より減速が緩い。ぼかしが最後まで少しずつ解け、焦点が合う過程が見える                  |
| 100ms / 80ms / 30ms 間隔         | 行 / 語 / 文字                | 単位が大きいほど間隔を広げる。30ms は約 2 コマで、これより広いと打ち込み表示に見える          |
| 105%                             | `line-mask`                   | 100% ちょうどでは、字の上端が窓の下端に 1px 残ることがある                                   |
| 12px                             | `blur-focus`                  | 字の太さより大きくぼかし、形が一度崩れて見える量。小さいと単に薄く見える                     |
| 0.25em / 0.5em                   | `blur-focus` / `char-stagger` | ぼかしだけでは向きが無く点滅に近い。字の大きさに比例させ、見出しの大きさが変わっても揃える   |

リードは 3 案とも透明度と 0.5em の浮上で、見出しの動きが半ばを過ぎてから出す。
和文の本文を 1 字ずつ出すと 24 字で 720ms 待たせ、ぼかすと細い字画ににじみが残るので、分けずにぼかさない。

見本の見せ方:

- Catalog の画面を縮めた模型ではなく、見出しとリードのテキストだけを置く。利用者が 2026-09-23 に、テキストで例示すればよいと判断した。
- 見出しは欧文、リードは和文にする。Catalog の見出しは欧文、本文は和文で組むためである。
- 見出しは 2 行に固定する。行単位の案があり、幅で折り返し位置が変わると比べられない。
- 見出しは typography token の title より大きい `clamp(2.5rem, 9vw, 5rem)` にする。動きの差は字面が大きいほど見分けやすい。公開面では使わない大きさなので token にしない。
- 読み込みで自動で 1 回再生し、「もう一度再生」で繰り返す。常に繰り返すと、見比べている間ずっと画面が動く。

### 削除した variant

却下した案はコードを削除し、仮説と軸だけを残す。

1 巡目の 3 案は、Catalog の画面を縮めた模型の本文を動かした。利用者の確認で全案を却下した。

- `fade`: 透明度だけで差し替わりの角が取れる。移動が無いので頻度が高くても疲れない。変えた軸: 本文全体、透明度のみ 120ms。
- `rise`: 透明度と 8px の浮上で、新しい面が来たことが伝わる。変えた軸: 本文全体、透明度と移動 200ms。
- `stagger-first`: 初回表示だけ見出しと区画を 40ms ずつ順に出し、切替は `fade` と同じにする。変えた軸: 初回と切替を分ける。

## Evaluation

比較評価は行わず、利用者が Motion 画面で 3 案を再生して判断した。
未確認の軸は、支援技術による読み上げの横断確認、reduced motion の実機での見え方、`filter` の描画負荷の計測である。

## Decision

3 案とも採用する。
Catalog 自身の画面の見出しには `blur-focus` を使う。

- 判断者: リポジトリの所有者
- 判断日: 2026-09-23
- 根拠: 利用者は「どれもいい感じ」と判断し、3 パターンとも作成して記載することを求めた。3 案は分ける単位が違い、行、語、文字の順に華やかさが増す。1 つに絞らず、場面に合わせて選べる型として残す。
- Catalog に使う案: 利用者が `blur-focus` を選んだ。エージェントの推奨は、単位が大きく `filter` を使わない `line-mask` だった。
- Motion 画面の載せ方: 3 案を切り替えずに縦に並べ、各案に仮説と変えた軸を添える。利用者が選んだ。

Catalog への適用:

- 見出し（`data-screen-heading` の `h1`）は、語ごとにぼかしから焦点を合わせる。
- 本文の区画も動かす。利用者が 2026-09-23 に、見出しだけでなく画面全体に効果を付けることを求めた。最初の適用は見出しだけで、本文を動かすと読む内容が待たされると考えていた。
- 区画の単位は各画面の根の直下の子にする。画面ごとの部品に手を入れずに、全画面へ同じ規則で効く。
- 区画は透明度と 24px（`space.600`）の浮上で出し、ぼかさない。見本の `blur-focus` もリードはぼかしていない。大きな面をぼかすと描画の負荷が増え（未計測）、本文の細い字画ににじみが残る。
- 区画の時間、曲線、間隔は見出しと同じ token にする。画面全体を 1 つの流れとして見せ、token も増やさない。
- 区画は見本のリードのように 450ms 待たせず、見出しの語と同じ 80ms 間隔で上から順に出す。画面は数十回開くので、本文が出るまで待たせない。5 つ目以降は 4 つ目と同時に出し、長い画面でも最後の区画を 320ms 以内に動き出させる。
- 24px は、見本のリードの 0.5em（約 8px）では区画の大きさに対して動いたと見えないためである。移動の距離の token は無いので、長さの階梯に寄せる。
- 配色の `<dialog>` は動かさない。閉じている間は `display: none` なので、animation を付けると開くたびに入場が最初から走る。
- サイドバーは動かさない。画面をまたいで同じ場所に留まることが、どこにいるかの手がかりになる。
- 語は空白で分ける。和文の題名は空白の無い一続きが 1 語になる。和文を 1 字ずつ分けると、長い題名ほど待たせる。
- 画面ごとに `App.tsx` で本文を key 付きで描き直し、同じ部品の画面どうし（方針 A から方針 B など）でも再生させる。key は `screenKey` なので、配色のダイアログの開閉では再生しない。
- 時間、間隔、曲線は token にした（`duration.entrance`、`duration.stagger`、`easing.entrance`）。公開 Catalog に実利用ができたためである（`tokens/motion/README.md` の追加規則）。
- `line-mask` と `char-stagger` の値は、公開 Catalog に実利用が無いので token にせず、variant 内の局所値のまま残す。

## Rejected reasons

- 1 巡目の 3 案（`fade`、`rise`、`stagger-first`）: 利用者は「イマイチ Motion の感じがわかりにくかった」と判断した。頻度を優先して 200ms 以下に抑えた結果、動いたこと自体が伝わらなかった。見せ方も、サイトの模型より見出しのテキストで例示するほうがよいと指示した。

## Learnings

頻度表の出発点に従うと、動きの目的が「印象」のときは、動いたこと自体が伝わらない。
目的が緩和なら短さが正しいが、利用者が求めたのは印象だった。
目的を 1 語で置く段階で、利用者の期待を確かめる必要があった。
