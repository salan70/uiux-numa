## Problem

授業スライド（Marp）の章扉は、章番号と題名だけで構成されている。
章が変わったことは分かるが、これから何を学ぶのかが絵で伝わらない。
教室で投影されるため、遠くからでも読める大きさと明快さが要る。
利用者が渡したテーマに沿って、章扉に置く挿絵を描き方の異なる複数案で作り、投影を想定した大きさで比較する。

題材は「ソフトウェアテスト」の章にする。
採用済みの技術アイコン `line-round` と同じスライドで並ぶため、線幅と端点の扱いが揃うかも比較の対象にする。

## Target

- 教員（利用者）: 章ごとにスライドを作る。同じ描き方で他の章（AI 駆動開発、データベースなど）にも展開したい。
- 学生: 教室の後方から投影された章扉を数秒見る。手元では PDF か Web で同じ画を見る。

## Scope / Domains

対象領域は illustration / SVG、visual design、consistency、accessibility。
題材と構図の役割は全 variant で共通にし、variant で変える軸は描き方だけにする。

- 線か面か、線幅、端点と角
- 情報量: 対象物だけか、場面（複数の要素と関係）か

## Constraints

- viewBox は `0 0 320 240`（4:3）。章扉では幅 360px 前後で表示する。
- 自己完結した静的 SVG にする。文字（`<text>`）を使わない。`just svg-check --viewbox "0 0 320 240"` を通す。
- 色は最大 3 色にする。線と面は `currentColor`（スライドの primary #002d62 を受ける）、強調は accent #ce1126、面の下地は #e7ebf1 とする。SVG 内では HEX で書く（`var()` は使わない）。
- 装飾として `aria-hidden="true"` で置く。意味は章番号と題名の文字が担う。
- 遠くから読めることを優先する。最小の線幅は 3、最小の隙間は 6 にする（320 幅での値）。
- 利用画面のモックは全 variant で同一にし、`diff` で確認する。章扉のスライド 1 枚と、手元で見る資料ページの図 1 枚を並べる。
- 書体とウェイトは `tokens/typography/` を使う。スライドと資料ページ固有の尺度は維持する。
- 編集用の原本を `variants/<id>/source/chapter.svg`、配布用を `variants/<id>/dist/chapter.svg` に置く。
- 部分編集の単位に `part-chapter-<role>` の id を付ける。色の部分編集の実証に使う。

## Hypothesis

章扉の挿絵は、文字が意味を担うので、絵は「これから扱う対象」を 1 つ示せば足りる。
情報量を増やして場面を描くと、投影では細部が読めず、手元でだけ意味が増える。
採用済みの技術アイコンと線幅の比を揃えると、同じスライドの中で調子が合う。
面で描くと投影で強いが、資料ページの小さい図では重く見える。

## Variants

題材（ソフトウェアテスト）と構図の役割は共通にし、描き方と情報量を変える。

| id            | 仮説                                                                              | 変えた軸                       | 実装                    |
| ------------- | --------------------------------------------------------------------------------- | ------------------------------ | ----------------------- |
| `line-object` | 線画で対象物 1 つだけを描けば、200px の資料ページでも構造が保たれ、投影でも読める | 情報量 = 対象物、描き方 = 線画 | `variants/line-object/` |
| `flat-scene`  | 面で場面を描くと投影で強く読めるが、資料ページの 200px では要素が潰れる           | 情報量 = 場面、描き方 = 面     | `variants/flat-scene/`  |

### 制作条件

2 案とも、描き方と情報量を担当者が指定し、Skill `crafting-svg` を読み込んだ subagent に 1 案ずつ任せた。
題材、viewBox、色の役割、利用画面のモックは共通。反復は最大 3 回。

### 描き方ごとの記録

#### line-object

描くもの: 期待と実際の突き合わせ。同じ大きさの 2 つが竿に載って釣り合う形で、一致の確認を示す。

- 線幅 5 は、採用済みの技術アイコン（viewBox 24、線幅 2）と表示時の実寸を揃えた値である。資料ページ 200px では 3.1px、章扉 360px では 5.6px になる。
- 要素は 4 つだけにした（ILLUS-05）。場面と背景を持たない（ILLUS-02）。
- 強調（`#ce1126`）は 1 か所で、「実際（作ったもの）」の側に置いた。左に置いて、文字から入った視線が最初に当たるようにした（ILLUS-07）。
- 支点は 2 つの対象より細く小さくして、主役を保った。

#### flat-scene

描くもの: 検査が進行している場面。済んだ項目、不具合が見つかった項目、これから検査する項目の 3 行。

- 要素は下地の面と 3 行だけに絞り、文字が担う「ソフトウェアテスト」を絵で繰り返していない（ILLUS-01、ILLUS-02、FORM-04）。
- 焦点は不具合 1 か所。光学的中心（幾何中心より上）に置き、判定の列を文字側に寄せた（FORM-01、ILLUS-05、ILLUS-07）。
- 強調は 3 段階に抑えた。焦点（赤のベタ面 42px）、済（紺のベタ面 34px）、未（紺の枠線のみ）の順である。
- 色の役割を先に決めた。`#e7ebf1` は後退する下地、`currentColor` は主体、`#ce1126` は焦点 1 か所である（ILLUS-06）。判定記号の抜き色に白ではなく下地の色を再利用し、3 色を守った。
- 線幅の比は技術アイコンと揃えなかった。同じ絶対幅を得るには viewBox 320 で線幅 1.8 が必要になり、Brief の最小線幅 3 を割るためである。代わりに端点と角の `round` と角丸の多用という形の言語で揃えた（FORM-07、ILLUS-08）。

| variant      | round | 観察                                                                                                     | 変更                                                                             | 参照               | 終了理由 |
| ------------ | ----- | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | ------------------ | -------- |
| `flat-scene` | 1     | 3 行のチェックリストは 200px でも構造が残るが、要素が等価に並び支配的な要素が不明瞭。UI のカードに見える | 行の役割を済、不具合、未に分け、焦点を中央行へ移し、未検査を枠線だけにした       | ILLUS-05、ILLUS-06 | 指摘あり |
| `flat-scene` | 2     | 階層は 3 段階に整理されたが、下地が全要素を囲うため「todo アプリの画面写真」に見える                     | 下地の面を幅 248 から 164 に縮め、3 本の項目が下地の右端を越えて重なるようにした | ILLUS-06、FORM-01  | 指摘あり |

### 仮説の検証

`flat-scene` の担当は「場面を描くと投影では細部が読めない」という仮説を部分的に反証した。
要素を 3 つに抑え、最小の要素を全体の約 10% の大きさに取れば、200px でも役割の差は読めた。
読めなくなるのは判定記号の折れ（チェックか x か）だけで、色と塗りの有無による区別は残る。
効くのは「場面かどうか」ではなく「要素数と最小の要素の相対サイズ」だった。

### 未解決と未検証

- `line-object`: 天秤の比喩が「比較」「公平」に読まれ、「テスト」に届くかは未検証である。
- `flat-scene`: 視線が右へ抜ける点は未解決である。下地が全要素を囲う形なら視線は閉じるが、カード感が戻る。3 回の上限に達したため選択を残した。
- `flat-scene`: チェックリストという比喩が「todo リスト」と取り違えられないかは未検証である。
- 実際の教室の投影距離での判読は未検証で、200px のシートを代理としている。
- 2 案とも、他の章（AI 駆動開発、データベースなど）へ展開したときに同じ描き方で作れるかは試していない。

## Evaluation

多観点の評価は行っていない。
判断は、2 案の比較グリッド（200px と 360px）と利用画面の確認による。
評価を経ない判断の扱いは[補足の ADR](../../docs/decisions/2026-09-17-named-variants-and-unevaluated-decisions.md)に従う。

## Decision

2 案とも採用しない。この Experiment は判断をもって終了する。

- 判断者: リポジトリの所有者
- 判断日: 2026-09-19
- 根拠: 2 案の比較グリッドと利用画面の確認

未評価の軸は次のとおり。
consistency、accessibility、visual hierarchy、brand fit のいずれも、多観点の評価を経ていない。
`just svg-check` を通ることと、200px と 360px で要素が判別できることは、制作時の自己確認で確かめている。

## Rejected reasons

2 案（`line-object`、`flat-scene`）を採用しなかった理由は次のとおり。

- 比喩が合わない: 天秤（期待と実際の突き合わせ）も検査表（進行中の検査）も、ソフトウェアテストの章を表すものとして合わなかった。
- 調子が合わない: 学生が読む資料の印象として、方向が合わなかった。
- 完成度が低い: 形の細部とバランスが粗い。

判断者と判断日は Decision と同じである。

## Learnings

- 章扉の挿絵は、機能アイコンより比喩の選択肢が広い。広い分、AI が選んだ比喩が利用者の意図と合う確率は下がった。題材（ソフトウェアテスト）を共有しても、そこから何を描くかで分かれる。
- 「場面を描くと投影では細部が読めない」という仮説は部分的に反証された。要素を 3 つに抑え、最小の要素を全体の約 10% の大きさに取れば、200px でも役割の差は読めた。効くのは「場面かどうか」ではなく「要素数と最小の要素の相対サイズ」だった。この知見は採用の可否と独立に残る。
- 線幅を技術アイコンと揃える方法は 2 案で分かれた。`line-object` は表示時の実寸を揃え（viewBox 320 で線幅 5）、`flat-scene` は実寸を揃えると最小線幅を割るため、端点と角丸という形の言語で揃えた。挿絵とアイコンの調和は、線幅の比でも実寸でもなく、どちらを揃えるかの選択になる。
- 却下した 2 案は学習材料として残す。
