# accessibility レビュー: 授業資料で使う技術アイコン

- 観点: accessibility
- 対象: line-round、line-square、solid、duotone
- 入力: README、variants/、previews/、docs/evaluation/axes.md
- 担当した軸: accessibility

## 観察

### 4 案に共通する事項（Mock.tsx、mock.css）

`Mock.tsx` の `Icon`（27〜36 行）は配布用 SVG を `<span className="ti-icon" aria-hidden="true">` に `dangerouslySetInnerHTML` で展開している。
`aria-hidden` は子孫ごと支援技術から外すので、SVG 側の `role="img"` と `<title>` は読み上げられない。
`Mock.tsx` に置かれた 16 箇所の `Icon` は例外なく可視テキストと隣接する（サイドバーの 8 項目が 44〜51 行、見出しの 3 箇所が 56〜69 行、章扉が 78 行でその直後に「第 3 章 / API と通信」、箇条書きの 4 項目が 86〜98 行）。
意味はすべて隣接テキストが担い、アイコンは装飾として正しく隠されているので、1.1.1 は 4 案とも満たす。

一方で配布用 SVG は 4 案 32 ファイルすべてが `role="img"` と日本語の `<title>` を持ち、`focusable="false"` は 0 ファイルである。
`role="img"` と `<title>` は単独で意味を持つ SVG の作法（UIFIT-04）、`aria-hidden` は可視ラベルと並べる場合の作法（UIFIT-05）で、モックは両方を重ねている。
支援技術には `aria-hidden` が勝つので害はないが、`<title>` はブラウザ標準の hover tooltip として残り、サイドバーでラベルと同じ文言が二重に出る。
ラベルなしで単独配置したときは `<title>` が名前になるため、この二層は資料への転用では利点にもなる。

同じアイコンが 2 箇所ずつ出るため、`part-*` の id は DOM 内でそれぞれ 2 回重複する。
WCAG 2.2 では 4.1.1 が廃止済みなので達成基準の違反ではないが、`getElementById` と将来の `aria-labelledby` は先頭しか拾わない。

`mock.css` の 184〜206 行はアイコンの寸法を `20px` などの絶対値で固定している。
ページ全体の拡大では追従するが、文字だけを拡大する設定ではアイコンだけ取り残される（1.4.4 の想定に対して弱い）。
`.ti-icon` の `flex-shrink: 0`（176 行）があるため、幅が狭まってもアイコンは潰れない（1.4.10 に有利）。
`mock.css` には `@media` が 1 つもなく、暗いテーマと `forced-colors` の指定は存在しない。

利用画面の各場面のコントラスト比は次のとおりで、非テキストの 3:1（1.4.11）はすべて満たす。
アイコンは常に可視ラベルを伴う装飾なので 1.4.11 は厳密には適用範囲外だが、参考として計測した。

| 場面                                | アイコンの色 | 隣接色    | 比      |
| ----------------------------------- | ------------ | --------- | ------- |
| サイドバー 20px                     | `#67676c`    | `#f6f6f7` | 5.21:1  |
| サイドバー 20px の現在項目          | `#3451b2`    | `#f6f6f7` | 6.56:1  |
| 見出しの前 24px                     | `#3c3c43`    | `#ffffff` | 10.94:1 |
| スライドの章扉 96px と箇条書き 32px | `#002d62`    | `#ffffff` | 13.53:1 |
| duotone の accent（サイドバー）     | `#ce1126`    | `#f6f6f7` | 5.21:1  |
| duotone の accent（本文とスライド） | `#ce1126`    | `#ffffff` | 5.63:1  |

20px では線幅 2 も抜き 2 も 1.67px になり、座標が整数でも 20/24 倍で画素境界に乗らないため、4 案とも antialiasing が避けられない。
実測した比は antialiasing 前の値であり、最小寸法では実効値がこれより下がる。

### line-round

`dist/*.svg` は `stroke="currentColor"`、`ai` の火花だけ `fill="currentColor"` で、直書きの色は 0 個である。
`just svg-check --mono` は 8 ファイルとも通る。
forced-colors では CSS の `color` が強制されるため `currentColor` は利用者の配色に追従し、UIFIT-07 の要求を満たす。

20px の 4 倍拡大（line-round-final-sheet.png の左から 2 列目）では、`branch` の節点が最も厳しい。
`circle r="2"` に線幅 2 なので内側の穴は直径 2 単位＝20px で 1.67px しか残らず、拡大図でも穴が 1 画素強である。
`web` は赤道と経線が作る格子が最も密で、隙間が 2〜3 単位である。
いずれも拡大図で線が接触しておらず、潰れてはいない。

### line-square

`butt` と `miter` で端点が角張るが、色の与え方は line-round と同一で直書きの色は 0 個、`--mono` も 8 ファイルとも通る。
20px の 4 倍拡大（line-square-final-sheet.png）では `branch` の正方形ノードの穴が 2×2 単位、`database` の 3 本の帯の隙間が 2 単位で、どちらも拡大図で白が残っている。
`terminal` と `web` が同寸の枠を共有するが、これは識別の論点であってコントラストと支援技術の伝達には影響しない。

### solid

`fill="currentColor"` のみで直書きの色は 0 個、`--mono` も 8 ファイルとも通る。
塗り面積が最大なので、antialiasing で細部の実効コントラストが落ちても形の判別に効く面が残る。

情報を担うのは負の空間で、`database` の溝と `web` の緯線経線と `test` のチェックが幅 2 単位＝20px で 1.67px である。
solid-final-sheet.png の 4 倍拡大では、明背景でも暗背景でも溝が白と黒の帯として残り、隣の塊と融合していない。
暗背景の列（同 png の 4 列目）では塗りが最も明るい塊になり、4 案の中で最も低視力に強い。

### duotone

`dist/*.svg` の 8 ファイルすべてに `fill="#ce1126"` が 1 個ずつ直書きされ、`just svg-check --mono` は 8 ファイルとも落ちる（設計どおり）。
`currentColor` の線は配色に追従するが、accent だけは追従しない。

1.4.1 は満たす。
accent はどのアイコンでも「そのアイコンにしかない意味」を担っていない。
`api` の戻り矢じりを単色にすると line-round の `api` と同じ往復矢印になり、向きで往復が読める。
`terminal` のカーソル、`branch` の分岐点、`database` のレコード、`test` の試料、`ai` の火花、`web` の節、`code` の斜線も、単色にすると形は残り意味は失われない。
サイドバーの現在項目（`Mock.tsx` 46 行）はブランド色と `font-weight: 600` の 2 つで示され、accent の赤は現在項目でも他項目でも同じなので状態を色だけで示してはいない。

一方で accent と線の間のコントラストは低い。
duotone/dist の 8 個のうち 4 個（`branch` の節点が幹の切れ目を埋める、`api` の矢じりが線の端に重なる、`test` の試料が三角フラスコの輪郭線に重なる、`web` の節が赤道と経線に重なる）は accent が `currentColor` の線に接触または重なる。
その境界の比は次のとおりで、いずれも 3:1 を下回る。

| 場面           | accent    | 接する線の色 | 比     |
| -------------- | --------- | ------------ | ------ |
| サイドバー     | `#ce1126` | `#67676c`    | 1.00:1 |
| サイドバー現在 | `#ce1126` | `#3451b2`    | 1.26:1 |
| 見出しの前     | `#ce1126` | `#3c3c43`    | 1.94:1 |
| スライド       | `#ce1126` | `#002d62`    | 2.41:1 |

サイドバーの 1.00:1 は輝度が完全に一致する組で、色相を知覚できない条件では accent と線の境界が消える。
P 型 2 色覚では `#ce1126` は `#574e24` 相当に暗くなり、白地とは 8.28:1 だが `#67676c` の線とは 1.48:1 になる。
D 型 2 色覚では `#83751c` 相当で、白地とは 4.64:1、`#67676c` の線とは 1.21:1 になる。
どちらも背景に対しては消えないので輪郭は保たれ、accent が線に溶けて単色版と同じ見え方になるだけである。
意味は失われないが、2 色にした狙いはこれらの条件では届かない。

暗背景と forced-colors には追従しない。
duotone-final-sheet.png の暗背景の列（背景 `#1a1a1a`）で `#ce1126` との比は 2.93:1 で、3:1 を下回る。
VitePress の既定の暗テーマの背景 `#1b1b1f` を仮に当てると 3.05:1 で、境界ちょうどである。
forced-colors の黒地（`#000000`）では `#ce1126` が 3.73:1 で、`currentColor` の線が 21:1 になるのに対し accent だけが最も弱い要素になり、利用者が選んだ配色の外の色として残る。
UIFIT-07 が引くとおり forced-colors は SVG の色を調整しないため、これは `var()` を避けた設計の帰結ではなく、直書き自体の帰結である。
README は「利用画面の CSS から `#part-*-accent` で上書きできる」と書いているが、`mock.css` にその上書きは 1 行もなく、`forced-colors` の `@media` も存在しない。
したがって現状の成果物には暗背景と forced-colors の手当てが無い。

20px の 4 倍拡大（duotone-final-sheet.png）では accent の形が最も早く失われる。
`ai` の 4 点星の accent は 20px で凹みが消えて赤い点に退化し、`api` の矢じりは約 2.5px の赤い三角になる。
`web` の節は赤道と経線の交点に重なるので、拡大図では線の上に乗った赤い塊に見える。
`test` は accent を輪郭線より後に描くため、フラスコ下部の黒い輪郭が赤で置き換わる（duotone-final-sheet.png の 96px 列で確認できる）。
いずれも「意味を持つ要素が読めなくなる」段階ではない。

## 論点

- duotone を採る場合、accent を暗テーマと forced-colors でどう扱うかを決める必要がある。選択肢は、利用画面の CSS に `@media (forced-colors: active)` と暗テーマ向けの `#part-*-accent` 上書きを置く、accent を `currentColor` に戻す、明テーマ専用と割り切る、の 3 つである。どれも実機（Windows のハイコントラストと VitePress の暗テーマ）での確認が要る。
- 配布用 SVG が `role="img"` と `<title>` を持ったままでよいかを決める必要がある。可視ラベルと並べる用途では hover tooltip がラベルと重複し、単独配置では名前として役立つ。ラベルありを既定にするなら `aria-hidden="true"` と `focusable="false"` を配布用に焼き込み、単独配置用を別に用意する案がある。
- `mock.css` がアイコンを px 固定にしている点を、実際の VitePress と Marp に移すときに `em` へ変えるかを決める必要がある。文字だけを拡大する利用者への影響が変わる。
- 20px での 1.67px 幅の細部（line 系の節点の穴、solid の抜き、duotone の accent）は、拡大図では潰れていないが、実際の学生のスマートフォンと教室のプロジェクタでの見え方は未検証である。README も 96px 専用版を作っていないと記録している。
- コントラスト比は `mock.css` の色を WCAG 2 の式で計算した値であり、レンダリング後の実測値ではない。最小寸法では antialiasing で実効値が下がるので、境界に近い duotone の暗背景については実測が要る。
- 第三者による識別テストが 4 案とも無い。accessibility の判定は計算と拡大図に基づくもので、低視力や色覚多様性の当事者による確認は含まない。
- 担当外の気づき: line-square の `terminal` と `web` が同寸の枠を共有する点、solid の `branch` が小文字の h に見える点、duotone のサイドバーで赤が 8 行の縦列になる点は、いずれも discoverability と visual hierarchy の論点として別観点に渡したい。
