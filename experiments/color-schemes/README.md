## Problem

実際の開発で使う配色の土台がない。
現状は variant ごとに HEX を直接書いている。
form-inline-validation では送信ボタンの色が揃わなかった。
その結果、consistency が課題ありになった。
配色を複数用意し、和名を付けて保持する。
プロダクトの性格に合わせて選び、実際の開発へ展開できる形にしたい。

最初に作った 4 variant は、人間の判断で評価の前に却下した。
既製の配色に見え、AI が作ったように感じられたためである。
確認すると、色相が Tailwind CSS v4 の既定パレットとほぼ一致していた。
経緯と値は Rejected reasons に書く。

2026-09 時点の前提は次のとおり。

- コントラストは WCAG 2.2 AA が実務の基準である。WCAG 3 のコントラストの算法は未定で、APCA は草案から外れた（[Adrian Roselli](https://adrianroselli.com/2026/04/wcag3-contrast-as-of-april-2026.html)）。
- 文字を持つボタンは、面や境界に 3:1 を求められない（[Understanding SC 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)）。
- CSS は `oklch()` を使える。`contrast-color()` は 2026-04 に Baseline になったが、黒か白しか返さない（[MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/color_value/contrast-color)）。
- Design Tokens Community Group の仕様は 2025.10 に初の安定版になり、OKLCH を扱える（[DTCG](https://www.w3.org/community/design-tokens/2025/10/28/design-tokens-specification-reaches-first-stable-version/)）。

## Target

配色を選ぶ開発者と、配色を当てた LP を訪れる利用者を想定する。

- 開発者: 個人開発で新しいプロダクトを始める。和名の配色から 1 つを選び、役割名のまま実装に持ち込む。
- 利用者: LP を初めて訪れる。OS のライト / ダーク設定と色覚の多様性を含む。

## Scope / Domains

対象領域は color、visual design、design tokens、accessibility。
variant で変える軸は見た目のうち配色だけにする。
配色は和の素材ごとに次の 4 つを変える。

- accent: 色相と、塗りが暗いか明るいか
- 面の色み: 素材の色相をどれだけ含むか
- 面の組み立て: 地に色を塗るか、カードを地と同じ色にするか
- 意味色との距離: accent の色相が意味色（成功、警告、エラー）に近いか

レイアウト、文言、文字、余白、操作は全 variant で共通にし、比較対象から外す。
配色の作り方も 1 つに固定し、比較対象から外す。

## Constraints

- React + TypeScript で実装し、追加の npm 依存を入れない。
- `LandingPage.tsx` と `layout.css` は和名の 10 variant で同一の内容にする。同一性は `diff` で確認する。
- 文字の共通 role は `tokens/typography/` を使う。hero、引用、価格の固有サイズは配色の比較条件として維持する。
- variant ごとの差は `scheme.css` と、`index.tsx` の配色のクラス名だけにする。
- LP は header、hero、機能、利用者の声、料金、更新情報の登録、footer で構成する。hero には製品画面の例を置き、意味色を使う。
- 製品名は架空の「Hako」とし、UI 文言は日本語にする。
- 色は下の役割表の CSS カスタムプロパティだけで定義する。`layout.css` に色の値を書かず、影と透明度も使わない。
- 各 variant はライトとダークを持ち、`prefers-color-scheme` で切り替える。
- 伝統色をそのまま使う値は HEX、明度と彩度を変えた値は `oklch()` で書く。すべて sRGB 色域内に収める。
- コントラストは WCAG 2.2 AA を満たす。8bit に丸めた sRGB から WCAG 2 の式で計算する。
- 役割は `:root:has(.cs-<variant-id>)` に定義する。実行基盤で variant を切り替えても、配色が混ざらないためである。

配色の作り方は次のとおり。

1. 和の素材を 1 つ選び、配色で表す素材の部分を決める（例: 山葵の根茎の皮、すりおろした身）。
2. 役割ごとに、用途と素材に合う伝統色を[和色大辞典](https://www.colordic.org/w)から選ぶ。候補はコントラスト目標を満たす色に絞る。
3. 目標を満たす伝統色がない役割だけ、最も意図に近い伝統色の色相を保ち、明度と彩度を変える。
4. 役割ごとに選んだ意図を Variants に書く。

最初の 4 variant では、色相と彩度に根拠がなかった。
色を 1 つずつ伝統色から選ぶことで、既定パレットの色相と高い彩度を避ける。

10 variant の 380 色のうち、301 色は伝統色をそのまま使った。
調整した 79 色は、ライトの 12 色とダークの 67 色である。
ライトは、警告の文字 10 色と、しんばしの線と文字 2 色である。
暗い黄の伝統色は緑みか茶みが強く、警告に見えなかった。
新橋色と同じ色相の暗い伝統色は、くすんでいて新橋色の鮮やかさを保てなかった。
ダークは、面、塗りの上の文字、下地である。
暗い面は、段差の揃った伝統色の組がなかった。

意味色は共通の組を決め、accent と区別しにくい variant だけ替える。

役割とコントラスト目標は次のとおり。
比は WCAG 2.2 の 1.4.3（文字）と 1.4.11（文字以外）に従う。

| 役割                    | 用途                                                          | コントラスト目標                               |
| ----------------------- | ------------------------------------------------------------- | ---------------------------------------------- |
| `--color-bg`            | ページの背景                                                  | なし                                           |
| `--color-bg-subtle`     | 交互のセクション背景、進捗バーの溝、未着手のチップ            | なし                                           |
| `--color-surface`       | カード、入力欄、副ボタンの背景                                | なし                                           |
| `--color-border`        | カードと区切りの線。装飾に限る                                | なし                                           |
| `--color-border-strong` | 入力欄と副ボタンの枠                                          | bg、bg-subtle、surface に 3:1                  |
| `--color-text`          | 本文と見出し                                                  | bg、bg-subtle、surface に 4.5:1                |
| `--color-text-muted`    | 補足の文                                                      | bg、bg-subtle、surface に 4.5:1                |
| `--color-accent`        | 塗りの accent。主ボタン、バッジ、ロゴ                         | なし。文字を持つため面の比は求めない           |
| `--color-accent-hover`  | 主ボタンの hover                                              | なし                                           |
| `--color-on-accent`     | 主ボタンとバッジの文字                                        | accent、accent-hover に 4.5:1                  |
| `--color-accent-strong` | 背景に置く accent。見出し上のラベル、告知、アイコン、進捗、枠 | bg、bg-subtle、surface、accent-subtle に 4.5:1 |
| `--color-accent-subtle` | 告知と機能のアイコンの背景                                    | なし                                           |
| `--color-focus`         | フォーカスの輪郭                                              | bg、bg-subtle、surface に 3:1                  |
| `--color-success`       | 完了のチップと登録完了の文言。背景は `success-subtle`         | success-subtle、surface、bg に 4.5:1           |
| `--color-warning`       | 期限間近のチップ。背景は `warning-subtle`                     | warning-subtle、surface に 4.5:1               |
| `--color-danger`        | 遅延のチップ。背景は `danger-subtle`                          | danger-subtle、surface に 4.5:1                |

塗りの accent と、背景に置く accent を分ける。
ゆずのような明るい黄色は、塗りでは暗い文字を載せて使える。
一方で、背景に置く線や文字としては比が足りないためである。
最初の 4 variant は、この 2 つを分けない旧い役割表で実装した。

## Hypothesis

役割ごとに意図を持って伝統色から選べば、既製の配色に見えない。
役割名とコントラスト目標は全 variant で固定する。
これにより、配色を差し替えても accessibility と visual hierarchy を保てる。
塗りの accent と背景に置く accent は分ける。
そうすれば、明るい accent も暗い accent と同じ LP で使える。
accent の色相が意味色に近いと区別しにくい。
彩度や色相の差でどこまで補えるかを確かめる。

Decision では採用を 1 件に絞らず、実際の開発の土台として残す配色を複数選んでよい。

`fuji` から `tsukiyo` の 5 variant は、利用者の依頼で後から追加した。
`wasabi` から `sumi` の 5 variant と大きく異なる、次の組み立てを含める。

- 地に色を塗る（`kingyo`）
- 補色を置く（`kingyo`）
- 地とカードを同じ色にする（`shinbashi`）
- ダークを主にする（`tsukiyo`）

以降の表は、役割ごとに選んだ伝統色と意図を示す。
「（調整）」は、その伝統色の色相を保って明度と彩度を変えた色である。
値は各 variant の `scheme.css` にある。

### 意味色の共通の組

成功、警告、エラーは、配色をまたいで同じ色で覚えられるよう共通にする。
accent と区別しにくい variant だけ、各 variant の表で替える。

| 役割           | ライト         | ダーク         | 意図                                                                                                               |
| -------------- | -------------- | -------------- | ------------------------------------------------------------------------------------------------------------------ |
| success        | 千歳緑         | 若竹色         | 常緑の松の落ち着いた緑で成功を示す。ダークは若竹の明るい緑にし、暗い地で読めるようにする                           |
| success-subtle | 白緑           | 千歳緑（調整） | 淡い緑の下地。ダークは千歳緑を暗くし、ライトと同じ緑の系統を保つ                                                   |
| warning        | 山吹色（調整） | 山吹色         | 山吹の花の黄で警告を示す。暗い黄の伝統色は緑みか茶みが強いため、ライトは山吹色の色相のまま文字に使える明度へ下げる |
| warning-subtle | 鳥の子色       | 黒茶           | 卵の殻のような淡い黄。ダークは暗い茶の下地で山吹色を浮かせる                                                       |
| danger         | 茜色           | 甚三紅         | 茜で染めた深い赤で、エラーを最も強い有彩色にする。ダークは紅花で染めた明るい赤                                     |
| danger-subtle  | 桜色           | 茜色（調整）   | ごく淡い赤み。ダークは茜色を暗くし、エラーの赤の系統を保つ                                                         |

### wasabi（わさび）

すりおろした山葵の淡い黄緑と、根茎の皮の深い青緑で組む。
蕎麦に添える薬味のように、清涼で控えめに効く配色にする。

| 役割          | ライト   | ダーク         | 意図                                                                                                       |
| ------------- | -------- | -------------- | ---------------------------------------------------------------------------------------------------------- |
| bg            | 白磁     | 濡羽色（調整） | ライトは白磁の器のように、緑をわずかに含む白。ダークは濡羽色の緑みの黒で、面に段差を作れるよう明度を上げる |
| bg-subtle     | 灰黄緑   | 濡羽色（調整） | 山葵の色相に近い灰みの帯で、地から一段沈める。ダークは地から一段明るくする                                 |
| surface       | 胡粉色   | 濡羽色（調整） | カードを地より明るくして浮かせる。ダークは帯よりさらに一段明るくする                                       |
| border        | 蕎麦切色 | 黒緑           | 山葵を添える蕎麦の灰緑。装飾の線なので地に溶け込ませる                                                     |
| border-strong | 山鳩色   | 山鳩色         | 灰緑のまま、ライトとダークのどの面にも 3:1 を超える。両方で同じ色にし、枠の印象を揃える                    |
| text          | 黒緑     | 白磁           | 緑を含む黒で、純黒より柔らかくする。ダークはライトの地の白磁を文字にし、明暗を入れ替える                   |
| text-muted    | 柳煤竹   | 深川鼠         | 本文と同じ緑の系統の灰で、補足を一段弱める                                                                 |
| accent        | 萌葱色   | 山葵色         | ライトは根茎の皮に近い深い青緑で、白い文字を載せる。ダークは山葵色そのもので、暗い地で最も目立たせる       |
| accent-hover  | 鉄色     | 裏葉柳         | 押す直前に、ライトは深く、ダークは明るくする。どちらも accent と同じ緑の系統にする                         |
| on-accent     | 胡粉色   | 濡羽色（調整） | ライトは貝殻の白。ダークは地と同じ黒で、明るい山葵色の上に載せる                                           |
| accent-strong | 萌葱色   | 山葵色         | ラベル、アイコン、進捗、枠を主ボタンと同じ色にし、accent の緑を 1 色に絞る                                 |
| accent-subtle | 白緑     | 萌葱色（調整） | ライトはすりおろした山葵を思わせる淡い黄緑。山葵色そのものは萌葱色の文字の下地には暗いため使わない         |
| focus         | 苔色     | 萌黄           | 若い茎の冴えた黄緑。深い緑の主ボタンと区別でき、面に 3:1 を超える                                          |

意味色は共通の組を使う。
成功の千歳緑は萌葱色より黄みに寄り、主ボタンと色相をずらしている。

## Evaluation

`docs/evaluation/review.md` の多観点の評価は行っていない。
判断は、色だけを並べた色見本ページと、LP の previews の確認による。

## Decision

和名の 10 variant をすべて採用し、実際の開発の土台にする配色とする。

- 判断者: リポジトリの所有者
- 判断日: 2026-09-17
- 根拠: 色見本ページと `previews/` の確認

判断の経緯は次のとおり。

- 利用者は LP の previews より先に、色だけを図形と文字に当てた見本での確認を求めた。
- 見本で `wasabi` から `sumi` の 5 variant を確認し、大きく異なるものを含む 5 variant の追加を求めた。
- 10 variant を見本で確認し、この組で進めると判断した。

採用時点の事実は次のとおり。

- 10 variant のライトとダークのすべてで、役割表のコントラスト目標（WCAG 2.2 AA）を満たす。
- 380 色のうち 301 色は伝統色をそのまま使い、残りは色相を保って明度と彩度を変えた。
- 多観点の評価を経ていない。brand fit、visual hierarchy、色覚の多様性での見え方は未評価である。

2026-09-20 に、14 variant の面と本文を共通の無彩色へ変更した。
ライトは白地と黒文字、ダークは黒地と白文字を基準にする。
通常の罫線と意味色も variant 間で共通にした。

variant 固有色は accent と focus に残す。
accent は塗り、文字、罫線に使う。
色付き文字と罫線には `accent-strong` または `accent-text` を使う。
フォーム境界の `border-strong` は無彩色のまま使う。

背景全体を variant 固有色で染める案は、成果より配色が先に見えるため却下した。
すべてを無彩色にする案は、variant の用途と比較可能性が失われるため却下した。

## Rejected reasons

最初の 4 variant（`cool-blue`、`warm-terracotta`、`vivid-violet`、`mono-ink`）は評価の前に却下した。

- 判断者: リポジトリの所有者
- 判断日: 2026-09-17
- 理由: 既製の配色に見え、AI が作ったように感じられた。

却下の後に値を確認した結果は次のとおり。

- accent と意味色の色相が、Tailwind CSS v4 の既定パレットとほぼ一致した。値は下の表のとおり。
- 色は既定値の複製ではない。色相と彩度を決めてから、明度を計算で求めた。ただし色相と彩度には外部の根拠がなかった。
- 紫の彩度は 0.24 で、色域の上限（0.26）と violet-500 の 0.25 に近い。
- 和名の 10 variant で、有彩色の accent に使った伝統色の彩度は 0.05〜0.19 である。

| 用途                | 最初の variant の色相 | Tailwind CSS v4 の色相 |
| ------------------- | --------------------- | ---------------------- |
| 青の accent         | 259                   | blue-500: 259.8        |
| 紫の accent         | 295                   | violet-500: 292.7      |
| テラコッタの accent | 40                    | orange-600: 41.1       |
| エラー              | 27                    | red-600: 27.3          |
| 成功                | 150                   | green-600: 149.2       |

## Learnings

- AI が根拠なしに色相と彩度を決めると、よく知られたフレームワークの既定パレットに寄り、既製に見える。色は役割ごとに外部の参照色から選び、選んだ意図を残す。
- 役割ごとに伝統色から選ぶと、380 色のうち 301 色は調整なしでコントラスト目標を満たした。伝統色で埋まらなかったのは、暗い黄の文字、ダークの段差のある面と下地である。
- 明るい accent（黄、淡い紫、水色）を使うには、塗りの accent と、背景に置く線や文字の accent を分ける必要があった。
- 配色の判断では、利用者は LP の画面より先に、色だけを図形と文字に当てた見本を求めた。配色の Experiment では、色見本を画面の preview より先に用意する。
- コントラスト検査、preview 撮影、色見本ページの生成のスクリプトは、リポジトリに置いていない。form-inline-validation と同じく、置き場は未定である。
