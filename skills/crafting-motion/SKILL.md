# 動きの実装

要求された動きを、通る順番を守って実装する。
最初の問いは「動かすか」である。動かさない判断も成果である。

## 参照

必要なものだけ読む。

- 対象 Experiment の README
- `skills/crafting-motion/references/recipes.md`
- `tokens/` と Brief が指定した配色
- 分岐が必要なら `skills/exploring-ui-variants/SKILL.md`
- 点検が必要なら `skills/reviewing-motion/SKILL.md`
- 評価の軸: `docs/evaluation/axes.md` の motion appropriateness、feedback quality

パスはリポジトリのルートからのものである。
`pick-ui-library`、`animate-expo`、`improve-animations`、`find-animation-opportunities`、`emil-design-eng` は呼び出さない。
部品が必要なら Brief と既存 Experiment の実装を見る。追加の npm 依存は Brief が禁じていれば入れない。

## 作者の仮説と要件

次は要件である。外すなら理由を記録する。

- `prefers-reduced-motion` を同時に入れる。理解を助ける変化は残し、位置の移動は弱めるか止める
- `:hover` の動きは `@media (hover: hover) and (pointer: fine)` で囲む
- 既存トークンがあればそれを使う。並行する easing / duration の定義を増やさない

次は作者由来の仮説である。必須要件にしない。外すときは頻度、目的、実操作の観察を書く。

- キーボード起点なら動かさない
- UI は 300ms 未満
- 入退場は `ease-out`、`ease-in` は使わない
- 動かす属性は `transform` と `opacity` に限る
- 候補を出さず 1 案に決める

数値と曲線の表は出発点である。表にない値が必要なときは、根拠を書いて局所的に使う。

## 手順

順番を守る。曲線の前に目的を決める。

### 1. 動かすか

利用頻度の目安は次のとおり。目安であり禁止ではない。

| 頻度の目安                    | 出発点                 |
| ----------------------------- | ---------------------- |
| 1 日に 100 回を超える操作     | 動かさない案を先に試す |
| 1 日に数十回                  | ごく短い変化か、なし   |
| たまに（ダイアログ、完了）    | 標準的な動きを検討する |
| 初めて / 稀（登録完了、祝福） | 喜びの予算を使ってよい |

キーボードから始まる操作でも、頻度と目的を見て決める。
登録完了のように稀なら、キーボードでも完了の因果が伝わる動きを候補にしてよい。
動かさないなら、即座の状態変化を実装して理由を書く。

### 2. 目的を 1 語で置く

次のいずれかにする。置けなければ動かさない。

- フィードバック
- 空間の連続
- 状態の明示
- 急な変化の緩和
- 説明（案内や初回だけ）
- 喜び（稀な操作に限る）

読み取り中のデータが、見た目のために動いてはならない。

実験では目的が同じでも手段が違う候補を残してよい。
各候補に目的と代償を 1 行で付ける。

### 3. 手段は安い順

上から見て、最初に足りるものを使う。

| 必要                             | 手段                                                          |
| -------------------------------- | ------------------------------------------------------------- |
| class や属性で足りる切替         | CSS transition                                                |
| マウント時の入場で JS 状態が不要 | CSS `@starting-style`                                         |
| 決まった軌道                     | CSS animation                                                 |
| 中断可能な制御                   | WAAPI                                                         |
| ばねやジェスチャ                 | 既存依存があるときだけ。新規ライブラリは Brief が許す場合だけ |

`height` の accordion など、transform で代替できない場合は例外として短くする。
性能は未計測なら断定しない。

### 4. 属性と原点

出発点は `transform` と `opacity` である。
`scale(0)` から始めない。`scale(0.9–0.97)` と透明度を組み合わせる。
トリガーに付く面は `transform-origin` をトリガー側にする。画面中央のモーダルは中央でよい。
`translate` のパーセントは要素自身の大きさ基準である。

親の CSS 変数で子の transform を一括駆動しない。対象要素へ直接書く。

### 5. 曲線と時間

入退場の出発点は強い `ease-out` である。
画面上の移動は `ease-in-out`、色の hover は `ease`、無限の進行は `linear` を出発点にする。

既存の token があればそれを使う。
なければ variant 内の局所値にする例は次である。リポジトリ共通 token にはしない。

```css
--ease-out: cubic-bezier(0.23, 1, 0.32, 1);
--ease-in-out: cubic-bezier(0.77, 0, 0.175, 1);
```

時間の出発点は次のとおり。

| 要素               | 時間         |
| ------------------ | ------------ |
| ボタンの押下       | 100–160ms    |
| 小さな面           | 125–200ms    |
| ドロップダウン     | 150–250ms    |
| モーダル、ドロワー | 200–500ms    |
| 説明、祝福         | 長くしてよい |

300ms を超える UI は理由を書く。理由があれば残してよい。

### 6. 中断と退場

連続で発火するものは keyframes より transition を優先する。
退場は入場と同じ経路を出発点にする。
利用者が決める相は遅く、システムの応答は速くしてよい。
連続操作と中断を実操作で確認する。

### 7. 同時に出す a11y

```css
@media (prefers-reduced-motion: reduce) {
  .element {
    animation: fade 0.2s ease;
  }
}

@media (hover: hover) and (pointer: fine) {
  .element:hover {
    transform: scale(1.02);
  }
}
```

減らす設定では移動を弱め、色と透明度の変化は残してよい。

## 出力

コードを書く。続けて短く書く。

- 頻度の判断と目的。動かさなかったものがあれば理由
- 手段、属性、曲線、時間。表から外れた値があれば根拠
- コードから判断できない感触。2〜5 倍速、コマ送り、実機のどれで見るか

性能、フレーム落ち、GPU を、計測なしで断定しない。

## 落とし穴

- `transition: all` は意図しない属性まで動かす。
- 表の数値を必須にして、完了画面の因果が消える。
- Motion ライブラリを Brief 無視で足す。
- reduced motion を後回しにする。
